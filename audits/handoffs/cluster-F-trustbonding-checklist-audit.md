## Scope

`TrustBonding` is the core emissions contract of the Intuition protocol. It manages TRUST token locks (raw "locked" balance) and distributes inflationary rewards pro rata to each user's time-weighted **veTRUST** (bonded) balance at the end of each epoch, scaled by system-level and personal **utilization ratios** sourced from the `MultiVault`. It extends a Solidity port of Curve/Stargate `VotingEscrow` and adds `PausableUpgradeable`. Rewards for epoch `n` are claimable **only** during epoch `n+1` (against the immutable veTRUST snapshot at `epochTimestampEnd(n)`), and are forfeited afterwards. Reward TRUST is custodied and paid out by the `SatelliteEmissionsController` (`transfer`, native TRUST); epoch/emission schedule math is delegated to the `CoreEmissionsController` via the satellite.

The v1.1.0 delta under review: **pause gating extended across every lock-taking entry point** (`deposit_for`, `create_lock`, `increase_amount`, `increase_unlock_time`, `increase_amount_and_time`, `withdraw_and_create_lock`, `claimRewards` — all `whenNotPaused`), while `withdraw` and `checkpoint` remain **deliberately un-gated**; the utilization-based reward model (system + personal ratios with self-healing carry sourced from `MultiVault`); and the per-epoch **budget cap** solvency backstop in `claimRewards`. External systems touched: `CoreEmissionsController`/`SatelliteEmissionsController` (schedule + payout; first-party, cluster H) and `MultiVault` (utilization getters; first-party). No ERC20/4626 vault share math, oracle, AMM, merkle, signature, or inline-assembly surface in this contract.

Per the handoff, legacy `VotingEscrow` is out of scope, **but** `TrustBonding` inherits its semantics; this review audits `TrustBonding` end-to-end and notes the inherited-parent boundary where it is load-bearing (lock decay, `deposit_for` token source, `unlock()` escape hatch, `onlyUserOrWhitelist`).

**Headline result:** no Critical, High, or Medium issue was confirmed on this surface. The §6.F invariants hold: total rewards claimed per epoch are **doubly bounded** by `_emissionsForEpoch(epoch) <= maxEpochEmissions` (the funded amount) — first structurally (`sum(pro-rata) <= emissions`), then by an explicit running budget cap; utilization ratios are in `[lowerBound, 10000]` and can only **scale emissions down**, never inflate claimable; veTRUST epoch-end snapshots are immutable historical reads that respect linear lock decay; and the pause asymmetry is exactly as specified (no funds trapped, accounting not stale). Findings are **3 Low + 6 Informational + 2 Open Questions + 1 config-risk**. The three frontier cluster-F items were reproduced and confirmed (see *Frontier-finding verification*).

## Findings

### [Low, config-contingent] `MINTIME` is set from the `_epochLength` init arg and is not tied to the emissions epoch length the snapshot-safety argument depends on (ref: SOL-Basics-Function-4, SOL-CR-7, SOL-Basics-Math-2)

- **Location:** `TrustBonding.sol:120-146` (`initialize` passes `_epochLength` as the **third** `__VotingEscrow_init` arg, which is `min_time`) → `VotingEscrow.sol:108-126` (`MINTIME = min_time`, `require(min_time >= 2 * WEEK)`). The *actual* emissions epoch length is read separately from `ICoreEmissionsController(satelliteEmissionsController).getEpochLength()` (`TrustBonding.sol:153-155,544,548,552`). Snapshot-safety NatSpec that relies on `MINTIME >= EPOCH_LENGTH`: `TrustBonding.sol:201-235`.
- **Impact:** `initialize`'s `_epochLength` parameter — documented in `ITrustBonding.sol:112` as "The length of an epoch in seconds" — is actually wired to the VotingEscrow **minimum lock time** (`MINTIME`), a *different* quantity from the epoch length that governs emissions (which comes from the controller and can be retuned there independently). The point-in-time epoch-end snapshot's anti-snipe guarantee (`totalBondedBalanceAtEpochEnd`, `userBondedBalanceAtEpochEnd`) is explicitly argued safe **because** `MINTIME >= EPOCH_LENGTH` forces any near-boundary lock to remain committed through the following epoch. Nothing in code enforces `MINTIME >= controller.getEpochLength()` — they are two independently-configured values across a contract boundary. If a deploy sets `MINTIME` (2 weeks) below a controller `epochLength` (> 2 weeks), a lock created just before an epoch boundary need only be held for `MINTIME` (< one full epoch), weakening the "committed through the following epoch" property the NatSpec asserts.
- **Exploit path:** Not permissionless-exploitable, and even under the misconfiguration the economic impact is **bounded, not theft**: veTRUST weight at the snapshot is `slope * (end - snapshotTs)`, so a short remaining lock yields proportionally *less* weight; there is no path to full-weight rewards without a genuinely long `end`. The concern is (a) the anti-snipe invariant the NatSpec advertises silently not holding, and (b) an operator being misled by the parameter name into a config where the two lengths diverge. The storage-layout test itself pins `MINTIME == TRUST_BONDING_EPOCH_LENGTH` (`tests/unit/TrustBonding/TrustBondingStorageLayout.t.sol:46`), confirming the coupling is real and load-bearing in the test rig but never asserted against the *controller's* epoch length.
- **Recommendation:** Either (i) validate at init / on controller update that `MINTIME >= controller.getEpochLength()` and revert otherwise, or (ii) rename the `_epochLength` init parameter to `_minLockTime` and update `ITrustBonding` NatSpec to remove the "epoch length" description, and add an explicit go-live assertion that `MINTIME` equals (or exceeds) the deployed controller epoch length. No steady-state source change is strictly required if deployment keeps them equal (both 2 weeks) — but the unenforced cross-contract invariant should be pinned by a deployment check + regression test.
- **Status:** Open — deployment-consistency gate; verify against the deploy manifests / upgrade scripts.

### [Low] `multiVault` is not set in `initialize`; utilization + emissions + claims for epoch >= 2 revert until the timelock calls `setMultiVault` (ref: SOL-Basics-Initialization-1, SOL-Heuristics-11)

- **Location:** `TrustBonding.sol:120-146` (`initialize` sets timelock, satellite, and both lower bounds, but **not** `multiVault`) vs. `TrustBonding.sol:506-508` (`setMultiVault`, `onlyTimelock`). `multiVault` is consumed by `_getSystemUtilizationRatio` (`:660-661`) and `_getPersonalUtilizationRatio` (`:610-611`), reached from `_emissionsForEpoch` (`:566`) and `claimRewards` for any epoch `>= 2`.
- **Impact:** Between `initialize` and the timelock's `setMultiVault`, `multiVault == address(0)`. Epochs 0 and 1 are special-cased to 100% utilization and do not touch `multiVault`, so early claims work — but the **first** epoch that requires a utilization read (epoch 2, i.e. the epoch-1 claim window closes / epoch-2 emissions compute) will revert on a call to `address(0)` if `setMultiVault` has not yet executed. Because `setMultiVault` is `onlyTimelock` (parameter timelock ≈ 3 days per handoff §3), the operational window to wire `multiVault` before epoch 2 is a hard deployment-ordering requirement, not a fire-and-forget default.
- **Exploit path:** Not attacker-reachable — this is a deployment/liveness footgun (uninitialized critical state that reverts, rather than silently mis-computes). Recorded per the checklist's "initialize all critical state" / "don't rely on a default that can also be a valid-looking zero" items.
- **Recommendation:** Either add `_multiVault` to the `initialize` signature (atomic wiring, consistent with the project's "prefer atomic initialization" rule) or add a go-live checklist item + verification-script assertion that `multiVault != address(0)` is committed via the timelock well before epoch 2 begins. A defensive `if (multiVault == address(0)) revert TrustBonding_ZeroAddress();` at the utilization read sites would convert the raw zero-address revert into a named one (clarity only).
- **Status:** Open — deployment-ordering gate.

### [Low] One-step `timelock` rotation and one-step `DEFAULT_ADMIN_ROLE` (ref: SOL-CR-6, SOL-Basics-AC-4)

- **Location:** `TrustBonding.sol:511-513` (`setTimelock`, `onlyTimelock`, one-step, no accept step) and the plain `AccessControlUpgradeable` admin model inherited via `VotingEscrow.sol:55,115` (no `AccessControlDefaultAdminRules`). Pause/unpause and every `onlyTimelock` setter depend on these two roles.
- **Impact:** `setTimelock` lets the current timelock hand the timelock role to a new address in a single call; a grant to a wrong/uncontrolled address permanently strands every `onlyTimelock` setter (`setMultiVault`, `updateSatelliteEmissionsController`, both utilization bounds, `setTimelock` itself). Likewise `DEFAULT_ADMIN_ROLE` (which controls `unpause`, whitelist, and the inherited `unlock()`) transfers via a one-step `grantRole`/`revokeRole` with no accept step. No attacker path — a privileged-operation footgun.
- **Recommendation:** Route both through the governance `TimelockController` (handoff §3 states this is the case, which mitigates at the governance layer) and/or adopt a two-step accept pattern for the timelock rotation. If governance is the sole holder, note as *mitigated at the governance layer* and close.
- **Status:** Open (likely Risk-accepted given the 4-of-8 Safe + `TimelockController` trust model in handoff §3).

## Frontier-finding verification (independent re-derivation)

The three known cluster-F items from the frontier round were re-derived from source and independently verified:

- **Fable-F-01 (Info — pause across an epoch boundary forfeits one epoch of rewards): Confirmed (dup Fable-F-01).** `claimRewards` is `whenNotPaused` (`TrustBonding.sol:383`) and targets **only** `prevEpoch = currentEpoch() - 1` (`:396`). If a pause spans the whole of epoch `N+1`, epoch `N`'s rewards are unclaimable during `N+1`; when unpaused in epoch `N+2`, `claimRewards` targets `N+1`, not `N`, and there is no path to reach `N` again (`_hasClaimedRewardsForEpoch` never set → but no function accepts `prevEpoch != currentEpoch-1`). The forfeited TRUST is reclaimed/burned via `getUnclaimedRewardsForEpoch` (`:355-376`), never stolen; no double-claim. Confirmed Informational, by-design tradeoff.
- **Fable-F-02 (Info — `deposit_for` lets a third party force-extend a victim's lock): Confirmed (dup Fable-F-02).** `deposit_for` (`TrustBonding.sol:448-450` override, adds `whenNotPaused`) delegates to `VotingEscrow.deposit_for` (`:382-389`), whose `_deposit_for` pulls tokens via `safeTransferFrom(_addr, address(this), _value)` (`VotingEscrow.sol:355`) — from the **lock holder**, not `msg.sender` — and, unlike the other lock-takers, carries **no** `onlyUserOrWhitelist` gate. A third party can therefore push a victim's already-approved TRUST into the victim's existing lock (increasing locked amount, not the unlock time), bounded by the outstanding ERC-20 allowance. Cannot mint or double-claim rewards; mitigation (tight allowances) is documented in the parent NatSpec (`VotingEscrow.sol:367-379`). Confirmed Informational, inherited Curve semantics.
- **Fable-F-03 (Info — system vs personal utilization view-time asymmetry, bounded): Confirmed (dup Fable-F-03).** `_getSystemUtilizationRatio` reads `getTotalUtilizationForEpoch(_epoch-1)`/`(_epoch)` (`TrustBonding.sol:660-661`) and `_getPersonalUtilizationRatio` reads `getUserUtilizationInEpoch(...)` (`:610-611`); the self-healing/lookback behavior lives inside the `MultiVault` getters (out of scope, cluster B/C — I could not fully trace the MultiVault-side lookback at this commit, hence **Medium confidence** on the asymmetry mechanism). Verified on the TrustBonding side that the impact is **bounded**: any utilization ratio (system or personal) is clamped to `[lowerBound, 10000]` by `_getNormalizedUtilizationRatio` (`:695-713`) and can only scale emissions **down** toward the funded `maxEpochEmissions`, and every claim is hard-capped by the per-epoch budget (`:420-429`). No solvency or conservation break. Confirmed Informational.

## Configuration risk (go-live decision)

### [Low, config-contingent] Utilization lower bounds + first-two-epoch full-pay are the only levers scaling total payout; confirm they are funded (ref: SOL-CR-7, SOL-Defi-Staking-2)

- **Location:** `TrustBonding.sol:555-570` (`_emissionsForEpoch`: epochs 0–1 pay `maxEpochEmissions` in full; epoch ≥ 2 scales by `systemUtilizationRatio`), `:739-757` (bounds validated to `[4000,10000]` / `[2500,10000]`).
- **Impact:** Solvency depends on the `SatelliteEmissionsController` actually custodying at least `maxEpochEmissions` worth of TRUST per epoch (TrustBonding never mints; it calls `transfer`, `:436`). Epochs 0 and 1 pay the *full* max with no utilization discount and no `MultiVault` dependency. If the satellite is under-funded for an epoch, otherwise-valid claims revert on the satellite's balance check (liveness), not a TrustBonding accounting break — but the funded-amount == `getEmissionsAtEpoch` assumption should be an explicit go-live check. The budget cap (`:420-429`) guarantees TrustBonding never *authorizes* more than `_emissionsForEpoch(epoch) <= maxEpochEmissions`, so the contract cannot over-pay even if the satellite holds a surplus.
- **Recommendation:** Add a deployment/verification assertion that per-epoch satellite funding ≥ `getEmissionsAtEpoch(epoch)`, and that `TrustBonding` holds `CONTROLLER_ROLE` on the satellite (else all claims revert). Parameterization/ops decision; no source change.
- **Status:** Open — go-live funding + role gate.

## Open questions for the developer

- **OQ-1 — Personal utilization target = *budget-capped claimed* amount, not eligible amount (ref: SOL-Defi-Staking-2, SOL-Heuristics-17).** `_getPersonalUtilizationRatio` uses `userClaimedRewardsForEpoch[account][epoch-1]` as the target the user's next-epoch utilization delta must exceed for a 100% ratio (`TrustBonding.sol:625-645`). A user who deliberately claims a *small* amount in epoch `N-1` sets a low bar and can hit 100% in epoch `N` with a small utilization delta; conversely a user who was eligible but skipped claiming (`target == 0`, prior eligibility > 0) is dropped to the floor (`:627-634`). This is bounded (ratios only scale down, budget-capped) and appears to be intended incentive design, but confirm the "claim small to lower your target" characteristic is acceptable and does not let a whale keep a permanently-low utilization bar while collecting near-max rewards.
- **OQ-2 — `sum(userBondedBalanceAtEpochEnd) == totalBondedBalanceAtEpochEnd` is assumed, and the budget cap is the backstop when it drifts.** Pro-rata `_userEligibleRewardsForEpoch = userBal * emissions / totalBal` (`:592`) relies on per-user veTRUST summing to the global veTRUST at the same timestamp. veCRV-style per-user slope rounding (`amount / iMAXTIME`, `VotingEscrow.sol:195,199`) vs the global weekly-stepped `_supply_at` can drift by dust, which the running budget cap absorbs (last claimer truncated). Confirm the intended invariant is "budget cap is authoritative for solvency" (it is, and is tested in `BoundaryAccounting.t.sol`) rather than "the two totals are bit-exact."

## Acknowledged non-issues (properties checked and cleared)

Each line is a §6.F / §5 hypothesis that was **attempted and refuted**, with the defending guard cited — the "we looked here and it held" evidence.

- **PASS — Per-epoch solvency: `sum(rewards claimed) <= per-epoch emissions budget`** (SOL-Defi-Staking-2, SOL-Basics-Math-5, handoff §5.2/§6.F). Tried to make total claimed for an epoch exceed `_emissionsForEpoch(epoch)`. Doubly defended: (a) structurally, `sum_i(userBal_i * E / totalBal) <= E` since `sum(userBal) ≈ totalBal` and each is further scaled by a `<= 100%` personal ratio; (b) explicitly, the running cap `alreadyClaimed >= epochBudget ⇒ revert` and `userRewards = min(userRewards, remainingBudget)` (`TrustBonding.sol:420-429`) truncates the marginal claimer. And `epochBudget = maxEpochEmissions * systemRatio/1e4 <= maxEpochEmissions` (the funded amount, `:555-570`). Tested in `tests/unit/TrustBonding/BoundaryAccounting.t.sol` (`EpochBudgetExhausted`, sum==total) and `TrustBondingIntegration.t.sol:162-164`.
- **PASS — No double-claim of an epoch** (SOL-Heuristics-12, SOL-Basics-Math-10). Tried claiming epoch `N` twice, and re-claiming after truncation. Defended: a successful claim always sets `userClaimedRewardsForEpoch[msg.sender][prevEpoch] = userRewards > 0` (`:433`; `userRewards == 0` reverts earlier at `:411`), and `_hasClaimedRewardsForEpoch` (`> 0`, `:572-574`) blocks any re-entry for that epoch (`:416`). An epoch is `prevEpoch` in exactly one `currentEpoch` window, so cross-window re-claim is structurally impossible.
- **PASS — Utilization carry / self-healing cannot inflate claimable or emissions** (handoff §6.F, SOL-Defi-Staking-2). Tried to push a ratio above 100% or emissions above the funded max across a no-activity gap. Defended: every ratio path returns `<= BASIS_POINTS_DIVISOR` (`:607,630,639,679,708,711`), `_getNormalizedUtilizationRatio` yields `[lowerBound, 1e4)` (delta<target guaranteed by the caller's `delta>=target` early-return), and `_emissionsForEpoch` multiplies `maxEpochEmissions` by `ratio/1e4 <= 1` (`:567`). System utilization is a **negative** feedback (higher prior claims ⇒ higher target ⇒ harder to hit 100% ⇒ lower emissions), never runaway. Fuzzed in `tests/unit/security/v1.1.0/TrustBondingClaim.t.sol`.
- **PASS — veTRUST balance-at-epoch-end respects lock decay and is immutable historically** (handoff §6.F, SOL-AM-ReentrancyAttack-1). Tried to retroactively inflate `_balanceOf(user, epochEnd(N))` after the fact. Defended: reward snapshots read `_epochTimestampEnd(N)`, a **past** timestamp during the `N+1` claim window; `_find_user_timestamp_epoch`/`_find_timestamp_epoch` (`VotingEscrow.sol:565-644`) locate the checkpoint `<= t` and later checkpoints (created at `block.timestamp > t`) never change that lookup; per-user decay is clamped at 0 past lock end (`:654-658`); global `_supply_at` walks only `slope_changes` up to `t` (`:725-748`). Future locks schedule only future slope changes. Snapshot is immutable.
- **PASS — Pause asymmetry: no funds trapped, accounting not stale** (handoff §6.F, SOL-CR-1/CR-2, SOL-Defi-Lending-4). Verified every lock-taker is `whenNotPaused` (`:448,454,460,466,472,481`) and `claimRewards` is `whenNotPaused` (`:383`), while `withdraw` (`VotingEscrow.sol:505`, `nonReentrant` only) and `checkpoint` (`:363`, `notUnlocked` only) are **un-gated**. Confirmed a user can always exit an expired lock while paused (principal never trapped), and global bookkeeping stays current. The only pause cost is one epoch's *reward* forfeiture across a boundary (Fable-F-01, Info).
- **PASS — Reentrancy on claim** (SOL-AM-ReentrancyAttack-2, SOL-Heuristics-4). `claimRewards` is `nonReentrant` (shared `ReentrancyGuardUpgradeable` with all VotingEscrow lock-takers), and all state writes precede the single external `transfer` (`:432-436`, strict CEI). A malicious `recipient` re-entering `claimRewards`/`deposit_for`/`withdraw` hits the shared guard; re-entering already-updated state hits `RewardsAlreadyClaimedForEpoch`.
- **PASS — Division-by-zero across reward + utilization + APY math** (SOL-Basics-Math-6). `_userEligibleRewardsForEpoch` guards `totalBalance == 0` (`:588`); `_getNormalizedUtilizationRatio` guards `target == 0` (`:707`, and every caller early-returns 100% before reaching it); `getUserApy` guards `locked <= 0` (`:292`); `getSystemApy` guards `_supply == 0` (`:341`). Only `getEpochLength() == 0` could divide-by-zero (config; reverts, not exploitable) — a controller-side concern (Fable-H-01, cluster H).
