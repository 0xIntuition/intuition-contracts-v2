## Scope

`AtomWallet` is an ERC-4337 smart account bound 1:1 to an atom (`termId`). Ownership is rooted entirely in the Coinbase Smart Wallet **MultiOwnable** model via `CoinbaseSmartWalletLib` (ERC-7201 storage at `0x97e2…`): owners are 32-byte addresses (ECDSA) or 64-byte P-256 public keys (WebAuthn/passkey). A single `_claimant` slot records the primary owner; `owner()` returns the AtomWarden pre-claim and `_claimant` post-claim so ERC-1271 integrations keep a single principal. The v1.1.0 delta under review: replacement of OZ `Ownable`/`Ownable2Step` with MultiOwnable + P-256/WebAuthn signature dispatch, the one-shot `completeClaim(onlyAtomWarden)` seed, the `owner()` pre/post-claim transition, `transferOwnership`, the signer-management surface (`addOwnerAddress` / `addOwnerPublicKey` / `removeOwnerAtIndex`), and `_validateSignature` / `isValidSignature`.

External systems touched: the ERC-4337 `EntryPoint` (set at init from trusted MultiVault `walletConfig`), `MultiVault` (`getAtomWarden`, `claimAtomWalletDepositFees`), and the deterministic `AtomWalletFactory` (CREATE2 BeaconProxy). No ERC20/4626, oracle, AMM, or bridge surface. Two low-level sites: `_call` (raw `call` + revert-bubble) and the library's `memory-safe` assembly for signature decode.

**Categories walked (7):** Attacker's Mindset (25), Basics — Initialization/Proxy-Upgrade/Access-Control subsets (135 file, relevant items), Heuristics (17), Signature (5), External Call (14), Low Level (5), Hash/Merkle-Tree (5, for the WebAuthn challenge). **Not loaded (6):** DeFi, Token, Integrations, Multi-chain, Centralization (covered by handoff §3 trust model), Timelock — no reachable surface in this contract. Partial walk by design.

**Headline result:** one **High** upgrade-migration hazard (LC-E-01 — new, characterized by an existing but *unfiled* regression test), one **Medium** (LC-E-02 — independently re-derived, dup of Fable-E-01), one **Low** (LC-E-03 — dup Fable-E-02), and three Informational (one new, two dup). Every §6.E auth-boundary hypothesis on the *steady-state* surface (pre-claim bypass, non-warden claim, owner-index edges, malformed WebAuthn, deploy/claim race, primary-owner lockout via the guarded path) was attempted and **refuted** with a cited defense; the one boundary that breaks is the legacy-claimed **upgrade migration**, not the permissionless surface.

## Findings

### [High] v1.1.0 beacon upgrade permanently bricks any legacy AtomWallet already claimed under the `Ownable2Step` model (ref: SOL-Basics-PU-9, SOL-Basics-PU-10, SOL-Heuristics-11; handoff §6.E "wedges completeClaim / locks out legitimate owners")

- **ID:** LC-E-01 · **Severity:** High · **Confidence:** Medium (mechanism High; real-world impact gated by an unverifiable precondition — see below) · **Status:** Open
- **Location:** `AtomWallet.sol:375-377` (`owner()` = `isClaimed ? _claimant : warden`), `:299-305` (`completeClaim` `isClaimed` guard), `:91` (`_claimant` at storage slot 3), `:83` (`isClaimed` at slot 1 off 20). Deployment: `script/intuition/v1.1.0/DeployCoreUpgradeImplementations.s.sol:453-458` (`_assertAtomWalletApplied` swaps the beacon impl with **no census / re-seed** of pre-existing claimed wallets). Behavior is already captured (as an *asserted* outcome, but **not filed as a finding**) by `tests/unit/security/v1.1.0/FrontierRound_WalletUpgrade.t.sol:128-165`.
- **Invariant broken:** §5.5 upgrade-safety in spirit (state that survives the upgrade must be interpreted consistently) and the §6.E auth boundary ("permanent DoS that wedges `completeClaim` or locks out legitimate owners").
- **Root cause:** The legacy (pre-v1.1) AtomWallet stored ownership in OZ `Ownable2StepUpgradeable` (ERC-7201 namespace `0x9016…9300`) and set the sequential `isClaimed` bool (slot 1, offset 20) to `true` on `acceptOwnership()`. The v1.1 layout is **append-only and slot-faithful** for the sequential vars (`forge inspect`: `multiVault@0`, `_entryPoint@1`+`isClaimed@1.20`, `termId@2`, new `_claimant@3` consuming the first former `__gap` slot, `__gap[49]@4-52`), and MultiOwnable lives in a *different* namespace (`0x97e2…`). So after the beacon swaps to the v1.1 implementation, for a wallet that was **claimed** under v1.0:
  - `isClaimed == true` **survives** (same slot),
  - `_claimant == 0` (its slot was legacy `__gap`, never written),
  - the MultiOwnable registry is **empty** (`0x97e2…` slot is `0`), and the legacy owner sits orphaned in the now-unread `Ownable` namespace.
  Therefore `owner()` returns `_claimant == address(0)`; `ownerCount() == 0`; `isOwnerAddress(legacyOwner) == false`. Every gated surface (`execute`, `executeBatch`, `withdrawDepositTo`, `claimAtomWalletDepositFees`, signer management) reverts `AtomWallet_OnlyOwnerOrEntryPoint` / `AtomWallet_OnlyOwner`, and `isValidSignature` returns `0xffffffff` for the legacy owner's key. Crucially, the **only** registry-seeding entry point — `completeClaim` — is gated by `if (isClaimed) revert AtomWallet_AlreadyClaimed()` (`:299-301`), so it cannot re-bootstrap the wallet. The `SOL-Heuristics-11` shape: the code assumes `isClaimed == true ⇒ _claimant` set, but the migration decouples the two, and `_claimant == 0` (the "unclaimed" default) is silently treated as a valid post-claim owner.
- **Impact:** Any native/ERC-20/ERC-721/1155 balance held by a claimed legacy wallet is **permanently locked**; the legitimate owner is locked out with no on-chain recovery short of a **further** beacon implementation upgrade (privileged, 7-day timelock). Accrued MultiVault deposit fees for that atom also become unclaimable (`claimAtomWalletDepositFees` routes to `owner() == 0` and is itself un-callable).
- **Proof of concept (existing, faithful):** `FrontierRound_WalletUpgrade.t.sol` — deploys the legacy `Ownable2Step` wallet, claims it (`transferOwnership`→`acceptOwnership` ⇒ `isClaimed = true`, owner = claimant), funds it 5 ETH, then `atomWalletBeacon.upgradeTo(newAtomWallet)`. Post-upgrade it asserts `owner() == address(0)`, `ownerCount() == 0`, the claimant's `execute` reverts `AtomWallet_OnlyOwnerOrEntryPoint` (funds stay put), `completeClaim(claimant)` reverts `AtomWallet_AlreadyClaimed`, and the legacy-owner signature yields `0xffffffff`. This is exactly the bricked end-state.
- **The crux / why confidence is Medium not High:** impact is real **only if** ≥1 AtomWallet was claimed under the legacy model **and** holds value on a target network (Intuition mainnet `1155` / testnet `13579`) at the beacon-swap block. That census cannot be taken locally (rules: no production reads). If the live claimed-legacy set is empty (e.g. claiming was never exercised in production, or all live wallets are still unclaimed — those migrate fine: `owner()` falls through to the warden and `completeClaim` can seed them), the finding is moot and downgrades to Informational. The severity is stated for the non-empty case, which the upgrade script does nothing to exclude.
- **Recommendation (pick one, in order of robustness):**
  1. **Migration path:** add a warden- (or admin-) callable one-shot that, when `isClaimed && ownerCount()==0`, reads the legacy `Ownable` owner from `0x9016…9300` (or takes it as a checked argument), sets `_claimant`, and `addOwnerAddress`es it — re-seeding MultiOwnable exactly once. Guard it so it can only run on a genuinely orphaned wallet.
  2. **Pre-upgrade gate:** census all deployed BeaconProxy wallets, assert **zero** are `isClaimed` under the legacy impl before `upgradeTo`, and fail the deploy dry-run otherwise (extend `_assertAtomWalletApplied`).
  3. At minimum, **file and track** this as a known upgrade constraint (it is currently only an asserted test outcome), and document that the beacon swap must precede any legacy claiming.
- **Regression test:** the existing `FrontierRound_WalletUpgrade.t.sol` characterizes the bricked state; a fix must flip `test_beaconUpgrade_claimedLegacyWalletLosesAllExecutableOwners` to a *recovered* state (owner restored, `execute` succeeds) and keep `completeClaimCannotMigrate…` only if option (2) is chosen. Mutation-check: the recovery test must go red if the re-seed helper is removed.
- **Variant sweep:** unclaimed legacy wallets — **safe** (fall through to warden + `completeClaim`); fresh v1.1 wallets — **safe** (`completeClaim`/`transferOwnership` always set a non-zero `_claimant`, checked at `:253,289`); claimed legacy wallets — **bricked** (this finding). ERC-1271 read path, UserOp path, fee-claim path — all inherit the empty-registry lockout.

### [Medium] ERC-1271 `isValidSignature` verifies the raw digest with no wallet binding — cross-wallet signature replay (ref: SOL-AM-ReplayAttack-2, SOL-Signature-1, SOL-Signature-4, SOL-Heuristics-6) — **Confirmed (dup Fable-E-01)**

- **ID:** LC-E-02 · **Severity:** Medium · **Confidence:** High · **Status:** Open · **Confirmed dup of Fable-E-01** (independently re-derived below).
- **Location:** `AtomWallet.sol:341-346` → `CoinbaseSmartWalletLib.sol:102-161` (EOA verify `:146`; passkey challenge `abi.encode(hash)` `:157`). The shipped-but-unused wrappers `replaySafeHash` / `domainSeparator` at `CoinbaseSmartWalletLib.sol:303,311`.
- **Invariant broken:** authorization boundary (§5) — a signature scoped to one account authorizes an action on a different account.
- **Independent re-derivation:** `isValidSignature(hash, signature)` calls the library with the **raw** `hash`. Nothing in the ERC-1271 path mixes in `address(this)` or `chainId` — verified by reading the full library path: it decodes `(ownerIndex, signatureData)`, looks up `ownerAtIndex`, and calls `SignatureCheckerLib.isValidSignatureNow(ownerAddr, hash, …)` (ECDSA) or `WebAuthn.verify({challenge: abi.encode(hash), …})` (passkey) — both over the unmodified `hash`. Acceptance is therefore a pure function of `(owner key, hash)`, **independent of which wallet is asked**. Upstream Coinbase Smart Wallet wraps the input in `replaySafeHash(hash)` (EIP-712 domain = `chainId` + `address(this)`) before verifying; this port drops that wrap while still shipping the helper. So if one key/passkey owns two AtomWallets `A` and `B` (the normal case — one EOA claims many atom wallets), a signature valid on `A` over digest `H` is **also** valid on `B` over `H`.
- **Impact:** cross-wallet approval/signature replay under any EIP-712 integration whose digest does **not** encode the wallet account. The NatSpec at `:333-336` explicitly claims "Compatible with EIP-712 integrations (Permit2, Seaport, etc.)". Permit2 `SignatureTransfer` signs token/amount/spender/nonce/deadline + the *Permit2* domain but **not** the owner account ⇒ replayable across a user's co-keyed wallets (funds risk). Seaport binds the offerer ⇒ unaffected.
- **Refutation attempted:** checked whether differing `owner()`/registry between two wallets rescues it (no — identical owner key ⇒ identical acceptance); whether the UserOp/ERC-1271 hash asymmetry blocks it (it blocks UserOp↔ERC-1271 reuse — `_validateSignature` prefixes `"\x19Ethereum Signed Message:\n32"` at `:498` while `isValidSignature` does not — but **not** ERC-1271↔ERC-1271 across wallets). Refutation fails.
- **Recommendation:** verify against `CoinbaseSmartWalletLib.replaySafeHash(hash, name, version)` (already implemented, binds `chainId`+`address(this)`) instead of the raw `hash`; the UserOp path should likewise wrap `userOpHash` (it is already wallet-bound via `userOpHash`, so unchanged risk, but consistency helps). If raw-digest verification must stay, **drop the Permit2 compatibility claim** from the NatSpec.
- **Variant sweep:** EOA owner — same bug; WebAuthn/passkey owner (`abi.encode(hash)` challenge) — same bug; ERC-1271 nested contract owner — same bug. UserOp path — safe (`userOpHash` binds `sender`+`chainId`+`nonce`, plus the EIP-191 prefix separates it from the ERC-1271 hash space).

### [Low] `transferOwnership` evicts the primary owner, bypassing the `removeOwnerAtIndex` primary-owner guard (ref: SOL-Heuristics-16, SOL-Heuristics-1) — **Confirmed (dup Fable-E-02)**

- **ID:** LC-E-03 · **Severity:** Low · **Confidence:** High · **Status:** Open · **Confirmed dup of Fable-E-02.**
- **Location:** `AtomWallet.sol:252-274` (`transferOwnership`, unconditional `CoinbaseSmartWalletLib.removeOwnerByAddress(oldOwner)` at `:268`) vs. the guard at `:407-412` (`removeOwnerAtIndex` → `AtomWallet_OwnerCannotBeRemoved`).
- **Invariant broken:** the advertised "primary `owner()` cannot be removed from the MultiOwnable registry" invariant (`:404-405`, `:408`).
- **Independent re-derivation:** `transferOwnership` is `onlyMultiOwnableOwnerOrSelf` (any registered co-owner or self). It reads `oldOwner = _claimant`, sets `_claimant = newOwner`, then calls `removeOwnerByAddress(oldOwner)` — the O(n) scan variant, which enforces **no** `owner()` guard and no `LastOwner` check. So a convenience co-signer at index 1 can call `transferOwnership(coSigner)`: the primary at index 0 is deleted and the co-signer becomes the primary, even though `removeOwnerAtIndex(0, abi.encode(primary))` reverts. The direct-removal guard is thus not a real trust boundary.
- **Impact:** Low — in the flat MultiOwnable model every registered owner is already fully privileged (`_checkMultiOwnableOwnerOrSelf` uses the same `isOwnerAddress` check for all), so eviction grants no *new* capability. The risk is a **false sense of protection** for operators who add convenience co-signers believing the primary is unremovable. No bricking: the eviction installs `newOwner` atomically (non-zero, checked at `:253`; `removeOwnerByAddress` cannot strand the wallet because the add either re-adds `newOwner` when `newOwner==oldOwner` or `newOwner` is added/kept).
- **Refutation attempted:** searched for a path where a co-owner is genuinely subordinate — none; tried to turn the eviction into a permanent brick (LastOwner underflow) — refuted: `transferOwnership` re-adds `newOwner` in the same tx and `newOwner != 0` is enforced, so `ownerCount` never sticks at 0.
- **Recommendation:** either make `transferOwnership` refuse to remove the current primary when `msg.sender != owner()`, or drop the misleading `removeOwnerAtIndex` primary-owner guard and document the flat trust model. Consistency over the specific choice.
- **Variant sweep:** `removeOwnerByAddress` is reachable only from `transferOwnership`; `renounceOwnership` is hard-disabled (`:280-282`).

## Configuration / go-live risk

### [High-contingent] The v1.1.0 beacon swap has no pre-flight census of claimed legacy wallets (ref: LC-E-01, SOL-Basics-PU-9)

`DeployCoreUpgradeImplementations.s.sol:453-458` swaps the AtomWallet beacon implementation and asserts only the impl pointer; it does **not** enumerate deployed BeaconProxy wallets or assert none are `isClaimed` under the legacy impl. Make "zero claimed-legacy wallets holding value on both target networks (or all such wallets migrated by the LC-E-01 recovery path)" an **explicit, evidenced go-live gate** before the beacon `upgradeTo`. This is the operational control that decides whether LC-E-01 is a live High or a moot Informational.

## Acknowledged non-issues (properties checked and refuted)

Each line is a §6.E / §5 auth-boundary hypothesis that was **attempted and refuted**, with the defending guard cited.

- **PASS — Pre-claim signature bypass / permissionless takeover** (SOL-Signature-4, SOL-Heuristics-11). Pre-claim the MultiOwnable registry is empty, so `isValidSignature` and `_validateSignature` return failure for *every* signature (`CoinbaseSmartWalletLib.sol:133-134` empty-owner → false). Confirmed by `AtomWalletTakeover.t.sol:39-55` and `AtomWalletAuthEdges.t.sol:263-266`.
- **PASS — Pre-claim `execute` by a non-owner** (SOL-Signature-4, SOL-EC-14). `onlyMultiOwnableOwnerOrEntryPoint` (`:455-462`): pre-claim only EntryPoint/self pass, and EntryPoint needs a valid sig (fails pre-claim). `AtomWalletAuthEdges.t.sol:278-283`.
- **PASS — Non-warden `completeClaim` / self-seeding** (SOL-Signature-4). `onlyAtomWarden` resolves `multiVault.getAtomWarden()` dynamically (`:464-468`); attacker call reverts `AtomWallet_OnlyAtomWarden`. `AtomWalletTakeover.t.sol:59-64`.
- **PASS — Double `completeClaim`** (SOL-Heuristics-12). `if (isClaimed) revert AtomWallet_AlreadyClaimed()` (`:299-301`); warden-of-record itself rejected (`:296-298`). `AtomWalletAuthEdges.t.sol:269-275`.
- **PASS — `completeClaim` reentrancy / re-order** (SOL-AM-ReentrancyAttack-2, SOL-EC-13). Strict CEI: `isClaimed = true` before `addOwnerAddress`, no external call inside `completeClaim` (`:303-310`).
- **PASS — Owner-index edge cases in signature validation** (SOL-LL-1, SOL-Heuristics-7). Library safe-decodes the `(uint256,bytes)` wrapper with explicit length/offset checks (`:105-129`), returns false for out-of-range/removed indices (empty owner bytes), and never reverts — preserving the ERC-4337 non-revert contract. Covered by `AtomWalletAuthEdges.t.sol:206-215` (out-of-range) and the F-002 regression (`git e86a0d2`).
- **PASS — Malformed / edge WebAuthn-P256 input** (SOL-HMT-3, SOL-LL-2). `WebAuthn.tryDecodeAuth` is non-reverting; a malformed blob yields an empty `clientDataJSON` ⇒ `verify` returns false ⇒ `isValidSignature` → `0xffffffff` (never a revert, never the magic). `AtomWalletAuthEdges.t.sol:163-202`; positive P-256 vector at `:220-256`. The challenge is `abi.encode(hash)` and the P256 malleability guard (`s ≤ N/2`) is enforced.
- **PASS — Primary-owner lockout via the guarded path** (SOL-Heuristics-16). `removeOwnerAtIndex` blocks removal of `owner()` (`:409-410`); `AtomWalletTakeover.t.sol:78-88`, `AtomWalletAuthEdges.t.sol:199-202`. (The *unguarded* eviction via `transferOwnership` is LC-E-03.)
- **PASS — `transferOwnership` bricking / `LastOwner` underflow** (SOL-Heuristics-3, SOL-AM-DOSA-1). Atomic remove-then-add with `newOwner != 0` (`:253-271`); the already-registered `newOwner` skip (`:269`) prevents an `AlreadyOwner` revert on ownership promotion; `ownerCount` never sticks at 0.
- **PASS — `completeClaim`-vs-factory-deploy race / hijack** (SOL-AM-FrA-2). The wallet address is the deterministic CREATE2 BeaconProxy (`AtomWalletFactory.sol:125-133`); `completeClaim` is `onlyAtomWarden`; AtomWarden reverts if the wallet is not yet deployed (`AtomWalletClaim.t.sol:61-69`). No attacker can front-run the seed or claim a different address.
- **PASS — AtomWarden rotation between deploy and claim** (SOL-EC-14). `owner()` pre-claim and `_checkAtomWarden` both read the *current* `multiVault.getAtomWarden()` (`:376,465`), so they track a rotated warden consistently; post-claim `_claimant` is immune to rotation. Trusted-admin action; no permissionless hijack.
- **PASS — EntryPoint-only path without a key** (SOL-Signature-4). `execute` accepts `msg.sender == EntryPoint` unconditionally, but `BaseAccount.validateUserOp` only lets the EntryPoint proceed after `_validateSignature` accepts an owner signature (`BaseAccount.sol:80-89`); a failing sig returns `SIG_VALIDATION_FAILED` and the op is rejected.
- **PASS — delegatecall / selfdestruct / tx.origin / fixed-gas call** (SOL-EC-3/6/10/11, SOL-Basics-PU-6, SOL-LL-3). None used. `_call` (`:509-516`) is a plain `call` that forwards all gas and bubbles the exact revert; target is owner-chosen (the owner is trusted to pick its own call targets). `_disableInitializers()` in the constructor (`:134-136`) locks the implementation (SOL-Basics-PU-5).
- **PASS — Reentrancy across `execute`/`executeBatch`/`claimAtomWalletDepositFees`** (SOL-AM-ReentrancyAttack-2). Shared `nonReentrant` (`:186,205,323`); a nested `execute → claimAtomWalletDepositFees` self-call reverts on the guard (documented at `:315-321`).
- **PASS — Storage-layout append-safety for the un-claimed / fresh path** (SOL-Basics-PU-9/PU-10). `forge inspect` confirms `_claimant@3` + `__gap[49]@4-52` = 50 reserved tail slots (matching the legacy `__gap[50]@3-52`), MultiOwnable in a disjoint namespace. Fresh and *unclaimed*-legacy wallets migrate cleanly; only the *claimed*-legacy case breaks (LC-E-01).
