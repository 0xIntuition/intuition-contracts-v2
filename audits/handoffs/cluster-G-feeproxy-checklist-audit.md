## Scope

`FeeProxy` is a **multi-tenant community fee router** sitting between periphery callers and the core `MultiVault` on the **deposit** and **creation** paths (redemptions are not proxied). Affiliates permissionlessly self-register (paying `registrationFee` to `treasury`), each owning a fee row (`depositBps`/`creationBps`/`depositFixedFee`/`creationFixedFee`) bounded by protocol caps (`maxBps ≤ 10_000`, `maxFixedFee`). A routing call takes `grossAssets` out of `msg.value`, computes `fee = grossAssets*bps/10_000 + fixedFee`, **pushes** the fee to the affiliate's `feeRecipient`, forwards `grossAssets - fee` to MultiVault (crediting the end user as share receiver / atom-triple creator), and refunds `msg.value - grossAssets` with a **push-then-pull-fallback** ledger (`pendingRefund` / `claimRefund` / `claimRefundTo`). Two pause surfaces exist: global `pause`/`unpause` and per-affiliate `pauseAffiliate`/`unpauseAffiliate` (pause on `PAUSER_ROLE`, unpause on `DEFAULT_ADMIN_ROLE`). It is `AccessControlUpgradeable` + `PausableUpgradeable` + `ReentrancyGuardUpgradeable`, TUP-proxied, atomically initialized.

**External systems touched:** first-party `MultiVault` only — `deposit` / `depositBatch` / `createAtomsFor` / `createTriplesFor` (native TRUST forwarded as `msg.value`), plus the `isApprovedToDeposit` / `isApprovedToCreate` approval reads. Native value is moved with OZ `Address.sendValue` (affiliate fee, treasury, refund-claim) and a raw `.call{value}` (refund push, so failure routes to the pull ledger). **No ERC20/4626 token handling, no oracle, no AMM, no signatures, no merkle, no inline assembly, no delegatecall.** TRUST is the native gas token on the Intuition chain, so this contract is pure native-value plumbing.

**Headline result:** no Critical/High/Medium confirmed on this surface. Per-transaction and cumulative ETH conservation hold (`fee + forwarded + excess == msg.value` on every routing path; the ledger is strictly `msg.sender`-keyed and CEI-ordered under `nonReentrant`); every §5.1 conservation and §6.G hypothesis was refuted with a cited defense. Findings are **1 Low + 4 Informational**, plus one config-risk note. The single frontier finding on this cluster (Fable-G-09) was independently reproduced and **confirmed (dup)**.

## Findings

### [Low] Admin/privilege transfer is one-step (`AccessControlUpgradeable`, no two-step accept) (ref: SOL-CR-6, SOL-Basics-AC-4)

- **Location:** `FeeProxy.sol:46-52` (inherits plain `AccessControlUpgradeable`, not `AccessControlDefaultAdminRules`); `DEFAULT_ADMIN_ROLE` gates `unpause` (`:474`), `unpauseAffiliate` (`:216`), and all three cap setters (`:443,451,458`).
- **Impact:** Handoff of `DEFAULT_ADMIN_ROLE` is a bare `grantRole(new)` + `revokeRole(old)` with no accept-step. A grant to a wrong/uncontrolled address, or a premature revoke, permanently strands the ability to `unpause`, `unpauseAffiliate`, or retune caps. Not attacker-reachable — a privileged-operation footgun.
- **Exploit path:** None (permissioned). Recorded per the checklist's two-step-transfer requirement.
- **Recommendation:** Adopt `AccessControlDefaultAdminRules` (two-step, delayed admin transfer) or drive admin through the governance `TimelockController`. Per handoff §3 the admin is a 4-of-8 Safe behind a `TimelockController`, so this is **mitigated at the governance layer**.
- **Status:** Risk-accepted (governance trust model, handoff §3 marks centralization out of scope). Filed for completeness.

### Informational

| # | Location | Note (checklist ref) |
|---|---|---|
| I-1 (LC-G-01) | `FeeProxy.sol:550-554`, `296,331,363,414` | **Stray/locked ETH is under-pay-only, never stealable — CONFIRMED dup of Fable-G-09.** `receive()` accepts native value only from `multiVault` or `address(this)`; there is no sweep. Independently reproduced: the payout legs (`_payAffiliate`, the `deposit*{value:}` forward, `_refundExcess`) move **`msg.value`-derived amounts**, never contract-balance-derived amounts; the only balance-based outflow is `_claimRefundTo`, which pays the caller's own **ledger** entry (`pendingRefund[msg.sender]`). So any ETH that MultiVault might refund back into `receive()` on a forward, or any residual, is **locked** (harms whoever overpaid) but can **never** inflate a refund or be swept by a third party — it cannot break §5.1 (never pay out more than taken in). Marked **Confirmed (dup Fable-G-09)**. Revisit only if MultiVault begins refunding forwarded value to callers. (SOL-Basics-Payment-7, SOL-AM-RP-1) |
| I-2 (LC-G-02) | `FeeProxy.sol:181,193,250,255,750-757` | **`feeRecipient == address(this)` / `== multiVault` is not rejected — affiliate self-footgun (new nuance, not in Fable-G-09).** `registerAffiliate` and `updateFeeRecipient` reject only `address(0)`. An affiliate that sets `feeRecipient = address(this)` sends its own accrued fee back into the proxy via `Address.sendValue` → `receive()` accepts it (sender is `address(this)`) → the fee is **locked** in the proxy. This only harms the misconfiguring affiliate (its own fee), is under-pay-direction (never over-pays a user, never breaks §5.1), and requires no attacker. Low-value hygiene: reject `address(this)` (and optionally `multiVault`) in `updateFeeRecipient`/`registerAffiliate` the way `claimRefundTo` already rejects `address(this)` at `:434`. (SOL-Heuristics-9, SOL-Basics-Function-1) |
| I-3 (LC-G-03) | `FeeProxy.sol:177-178,277-278,316-317,350-351,384-385` | **Modifier order `whenNotPaused nonReentrant` (guard not first).** SOL-Heuristics-4 recommends `nonReentrant` precede other modifiers. Here `whenNotPaused` runs first, but it is a **pure state read** (`_requireNotPaused` reads the namespaced `_paused` slot) with no external call and no state mutation, so no reentrancy window is opened before the guard is set. No exploit; recorded so the deviation from the heuristic is a conscious, documented non-issue. (SOL-Heuristics-4) |
| I-4 (LC-G-04) | `FeeProxy.sol:742-744` | **`_calcFee` multiplication is unbounded before the div.** `grossAssets * bps` is checked-arithmetic (0.8.29) and would revert on overflow, which is only reachable for `grossAssets` near `type(uint256).max` — impossible for real native TRUST bounded by `msg.value ≥ grossAssets`. No precision loss beyond the intended floor division (fee rounds **down**, favoring the user/forwarded amount). Recorded as an acknowledged edge, not a defect. (SOL-Basics-Math-7, SOL-Basics-Math-12) |

### Configuration risk (go-live decision)

### [Low, config-contingent] `setMaxFixedFee` has no upper bound; caps rely on the caller `FeeGuard` for per-call protection (ref: SOL-CR-7, SOL-Basics-Function-1)

- **Location:** `FeeProxy.sol:451-455` (`setMaxFixedFee` accepts any `uint256`; contrast `setMaxBps` at `:443-448`, bounded by `BPS_DIVISOR`).
- **Impact:** A misconfigured (or hostile-but-trusted) admin could raise `maxFixedFee` arbitrarily, letting affiliates set very large fixed fees. This is **bounded on the user side** by three independent guards, so it is not a theft vector: (1) every routing call requires the affiliate's configured fee ≤ the **caller-supplied `FeeGuard`** (`_assertFeeGuard`, `:730-737`) — a caller passing a tight guard is fully protected against a fee change/front-run between quote and execution; (2) `fee ≥ grossAssets` reverts `FeeProxy_FeeExceedsGross` (`:291,598`) so a call can never forward zero/negative to MultiVault; (3) the fee is deducted **from** gross, never added on top, so the user's maximum outflow is exactly `msg.value`.
- **Recommendation:** Consider a sane absolute ceiling on `maxFixedFee`, and make "callers must pass a real `FeeGuard`, not `type(uint256).max`" an integration guideline. No source change strictly required given (1)–(3).
- **Status:** Open — parameterization/integration guidance; governance-gated (handoff §3).

### Open questions for the developer

- **OQ-1 — `feeRecipient`/`treasury` reverting `receive()` bricks the affiliate's own path (by design?).** `_payAffiliate` (`:755`) and the `registerAffiliate` treasury forward (`:197`) use `Address.sendValue`, which **reverts** the whole routing/registration call if the recipient rejects native value. This is deliberate (NatSpec at `:746-749`: a bricked recipient is the affiliate's problem, and it fails safe — no funds move). Confirm this is the intended UX: an affiliate whose `feeRecipient` later becomes a reverting contract wedges **all** of its own routing until it calls `updateFeeRecipient` (still callable while paused/globally-paused). No protocol-fund risk; user routes to other affiliates are unaffected.
- **OQ-2 — Read-only reentrancy on analytics during `_payAffiliate` (accepted?).** `_payAffiliate` (external send to the affiliate-controlled `feeRecipient`) executes **before** `_recordAffiliateStats` and before `_refundExcess` on every routing path (`:294→298`, `:329→335`, `:361→367`, `:412→418`). A hostile `feeRecipient` re-entering a **view** (`affiliateStats`, `affiliateUserStats`, `pendingRefund`) observes pre-increment counters. Confirm no off-chain/on-chain consumer treats these analytics as settlement-grade — they are documented as dashboard counters, and `nonReentrant` blocks all **state-changing** reentry, so this is inert today. Flagged so it stays inert if a consumer is later added. (SOL-AM-ReentrancyAttack-1, SOL-EC-1)

## Acknowledged non-issues (properties checked and cleared)

Each line is a §6.G / §5.1 hypothesis that was **attempted and refuted**, with the defending guard cited and — where a suite test exists — the green test named. All 10 existing FeeProxy security tests were re-run green during this review (`tests/unit/security/v1.1.0/FeeProxy{Conservation,MultiVault}.t.sol`).

- **PASS — Per-transaction ETH conservation (never pay out more than taken in)** (SOL-AM-RP-1, §5.1). On every routing path the outflows sum to exactly `msg.value`: `fee` (`_payAffiliate`) + `forwarded` (`deposit*{value:}`) + `excess` (`_refundExcess`) where `forwarded = gross - fee` and `excess = msg.value - gross`. `depositVia:290-299`, `_setupRoutingFlow:597-604`, batch/create `:329-336,361-368,412-419`. Verified by `testFuzz_depositVia_conservesEth` (10k runs, zero-sum over {caller, recipient, vault, proxy}, proxy residual == 0).
- **PASS — Cumulative conservation / no draining a locked residual** (§5.1). The only balance-based payout is `_claimRefundTo` paying `pendingRefund[msg.sender]`; that ledger is credited **only** in `_refundExcess` on push failure, by exactly the wei that stayed in the contract (`:762-768`). No path credits the ledger without matching retained ETH, so `Σ claimable ≤ balance` always; stray/locked ETH (I-1) is never claimable. Verified by `test_pendingRefundEqualsOverpayment_notMore`.
- **PASS — Double-claim / claim-after-push** (SOL-Heuristics-12, SOL-EC-13). `_claimRefundTo` zeroes `pendingRefund[msg.sender]` **before** `Address.sendValue` (CEI) and both entry points are `nonReentrant` (`:425,430,611-619`); a second claim reverts `FeeProxy_NoRefundOwed`. Push only credits the ledger on failure, so a successful push leaves nothing to claim. Verified by `test_doubleClaim_reverts`.
- **PASS — Cross-user `pendingRefund` attribution** (SOL-Heuristics-3, SOL-Basics-AC-2). Ledger is keyed by `msg.sender` on both credit (`_refundExcess(user=msg.sender)`) and debit (`_claimRefundTo` reads `pendingRefund[msg.sender]`). `claimRefundTo(recipient)` moves **only** the caller's own balance to `recipient` (SCW recovery) and rejects `recipient == address(this)` (`:434`). Verified by `test_crossUserCannotDrainPendingRefund`.
- **PASS — Refund-push reentrancy** (SOL-AM-ReentrancyAttack-2, SOL-EC-13). `_refundExcess` uses a raw `.call{value}` to `msg.sender` (the only untrusted push target) as the **last** external action before `emit`, and the whole routing frame is `nonReentrant`; a malicious caller/`feeRecipient` re-entering any routing or claim path reverts `ReentrancyGuardReentrantCall`. Verified by `test_maliciousFeeRecipient_cannotReenterFeeProxyDuringAffiliatePayment`.
- **PASS — Routing value onto a non-approving receiver/creator** (SOL-Basics-AC-2, SOL-EC-14). Deposits: `_assertDepositReceiverApproved` requires the receiver to have approved the proxy on MultiVault, **and** (delegated `receiver != msg.sender`) to have approved the caller (`:686-696`). Creations: `_assertCreatorApproved` requires the creator (`= msg.sender`) to have approved the proxy (`:699-705`); creator is bound to `msg.sender`, never routable to a third party. MultiVault re-checks proxy authority (defense in depth). Verified by `test_maliciousFeeRecipient_cannotDepositIntoVictimReceiverWithoutVictimApproval` (`MultiVault_SenderNotApproved`).
- **PASS — Partial-batch composition with MultiVault** (SOL-Basics-AL-10, SOL-Heuristics-16). The affiliate fee is paid **before** the batch `deposit*/create*` call, so any downstream leg revert unwinds the entire tx atomically — fee rolls back, no partial mint, no stat inflation, proxy retains nothing. Verified by `test_depositBatchVia_revertsAtomicallyWhen{DownstreamMinSharesFails,AllocatedLegFallsBelowMultiVaultMinimum}` and `test_createTriplesVia_revertsAtomicallyWhenSecondLegDuplicatesFirstLeg`.
- **PASS — Rounding direction in bps + allocation** (SOL-Heuristics-10, SOL-Basics-Math-4/Math-5, SOL-Basics-AL-12). `_calcFee` floors the bps portion (fee down → forwarded up, favors user/protocol). `_allocate` distributes proportionally and assigns the rounding **dust to the last leg** so `Σ forwardedAssets == totalForwarded` exactly; `_sum` rejects any zero leg so dust cannot be shipped to a zero-gross slot. Verified by `test_depositBatchVia_roundingDustMatchesDirectMultiVaultForwardedAssets` (byte-equal to the direct MultiVault path; proxy holds no dust).
- **PASS — Global vs per-affiliate pause interaction** (SOL-CR-2). `whenNotPaused` gates the five value/registration entry points; `_requireActiveAffiliate` independently blocks a paused affiliate's routing. Recovery paths (`claimRefund`/`claimRefundTo`) and rehab paths (`updateAffiliateFees`/`updateFeeRecipient`) are **not** `whenNotPaused`, so users recover refunds and affiliates fix rows during either pause. Pause is `PAUSER_ROLE`, unpause is the tighter `DEFAULT_ADMIN_ROLE` (asymmetric by design, `:469-476,205-224`). No user position is stranded (redemptions bypass the proxy entirely).
- **PASS — Execution-time cap re-check** (SOL-Basics-AC-5, SOL-CR-7). Routing re-asserts the **current** protocol cap against the side actually consumed (`_assertSideWithinCaps` in `depositVia:287` and `_setupRoutingFlow:589`), so a `setMaxBps`/`setMaxFixedFee` drop immediately blocks now-over-cap rows until the affiliate lowers its row — no grandfathering.
- **PASS — Fee-guard front-run protection** (SOL-Basics-Function-3, SOL-AM-FrA-1). The caller-supplied `FeeGuard` bounds the affiliate's configured fee at execution (`_assertFeeGuard:730-737`), defending against a fee bump or front-run between quote and execution.
- **PASS — `msg.value` underflow / payment accounting** (SOL-Basics-Payment-2, SOL-Basics-Math-7). Every path checks `msg.value ≥ gross` before subtracting (`depositVia:284`, `_setupRoutingFlow:595`); `registerAffiliate` requires `msg.value == registrationFee` exactly (`:184`). No `msg.value` used inside a loop (SOL-Basics-AL-11) — the batch legs consume the pre-summed `totalForwarded`.
- **PASS — `receive()` sender gating; no fallback** (SOL-Basics-Payment-3, SOL-Basics-Function-6). `receive()` reverts `FeeProxy_UnauthorizedEthSender` for any sender other than `multiVault`/self (`:550-554`); there is **no** `fallback`, so calls with unknown selectors or arbitrary calldata revert. Force-feeding via `selfdestruct` remains theoretically possible (as for any contract) but only adds to the locked-under-pay residual (I-1) — never over-pays.
- **PASS — Initialization / proxy hygiene** (SOL-Basics-PU-2/3/5, SOL-Basics-Initialization-3). `constructor` calls `_disableInitializers` (`:117-119`); `initialize` is `initializer`-gated, uses the `*_init` upgradeable parents, validates zero addresses and `maxBps ≤ BPS_DIVISOR`, and grants both roles to `admin_` (`:136-164`). Front-running the initializer is closed by atomic TUP construction (deploy script / test harness `FeeProxyBaseTest:101-113`).
- **PASS — Storage-layout upgrade safety** (SOL-Basics-PU-9/10). `forge inspect` confirms slots 0–9: `multiVault, treasury, maxBps, maxFixedFee, registrationFee, _affiliateConfigs, pendingRefund(slot 6), _affiliateStats, _affiliateUserStats, __gap[50]`. `pendingRefund` at slot 6 matches the pinned `PENDING_REFUND_SLOT` in `FeeProxyBaseTest` and the `FeeProxyUpgradeRegression` suite; the OZ 5.4.0 parents use namespaced ERC-7201 storage, so the proxy's own vars start at slot 0. Append-only, `__gap` present.
- **PASS — Admin cannot pull user/affiliate funds** (SOL-CR-3, SOL-AM-RP-1). There is no admin withdrawal/sweep path; the only value movers are the fee/forward/refund legs (all `msg.value`-derived) and the user-keyed `claimRefund*`. Admin powers are cap/pause/registration-fee only.
