## Scope

`MultiVault` is the core Intuition protocol contract: it creates atom/triple terms and manages their bonding-curve vaults, using native **TRUST** (the Intuition-chain gas token) as the base asset. The v1.1.0 heavy write-path bodies (`createAtoms`, `createTriples`, `createAtomsFor`, `createTriplesFor`, `deposit`, `depositBatch`, `redeem`, `redeemBatch`, and their transitive call graph) live in the linked `MultiVaultLib` and are reached by `DELEGATECALL`, executing in `MultiVault`'s storage/`msg.sender`/`msg.value` context.

Cluster A is the **payable multicall + per-leg value accounting** surface introduced in v1.1.0:

- `multicallPayable(bytes[] data, uint256[] values)` — enforces `sum(values) == msg.value`, dispatches each leg by `delegatecall` to `address(this)` (preserving `msg.sender`), and virtualizes the per-leg value in transient storage.
- `_virtualMsgValue` / `_inMulticall` — EIP-1153 transient slots; `_effectiveMsgValue()` returns `_inMulticall ? _virtualMsgValue : msg.value`, and every migrated payable forward reads it.
- The payable-selector allowlist `{createAtoms, createTriples, createAtomsFor, createTriplesFor, deposit, depositBatch}`.
- Canonical `multicall(bytes[])` override (non-payable) that forces `_virtualMsgValue = 0` and shares the `_inMulticall` guard.
- Adjacent surface reviewed whole-contract: on-behalf-of creates and their attribution, the system-utilization epoch rollover guard (`hasRolledOverSystemUtilization` / `lastSystemUtilizationEpoch`), `PAUSER_ROLE` + `onlyTimelock` setters, `reinitialize(2)`, `sweepAccumulatedProtocolFees`, `claimAtomWalletDepositFees`, and the approval bit-flag path.

**Invariant focus:** §5.6 (no `msg.value`-replay in `multicallPayable`) and §5.1 (conservation of value). Cluster C (`DynamicFeeFlatPriceCurve` + `IBaseCurve` record/quote hooks) is **absent at this commit** (confirmed against `src/` and the frontier scope-reconciliation), so the handoff's "re-enter via curve record hook" branch of the §6.A surface has no code and is moot here; the atom-wallet-factory branch is present and was reviewed.

External systems touched from cluster-A-reachable paths: `ITrustBonding.currentEpoch()` (epoch source), `IBondingCurveRegistry` (price/preview/limits), `IAtomWalletFactory.computeAtomWalletAddr` (deterministic address), `IAtomWallet.owner()` — all first-party, protocol-deployed, and only ever **view** calls on the payable legs. No ERC20/4626, oracle, AMM, bridge, or merkle surface.

**Headline result:** no Critical, High, or Medium issue was confirmed on this surface. The per-leg value virtualization, transient scoping/clearing (including caught reverts and re-entry attempts), nested-multicall rejection, selector allowlist, and off-by-one guards are correctly implemented, and every §5.6/§5.1 High/Critical hypothesis was refuted with a cited defense and an existing passing test. Findings are **1 Low + 3 Informational** (two of which independently confirm frontier informationals), plus 1 config-risk item and 2 open questions.

## Findings

### [Low] `redeem` / `redeemBatch` are `whenNotPaused` — an emergency pause freezes user withdrawals (ref: SOL-CR-1, SOL-CR-2)

- **Location:** `MultiVault.sol:736-749` (`redeem`, `whenNotPaused nonReentrant`), `MultiVault.sol:751-765` (`redeemBatch`, same). Pause is armed by `PAUSER_ROLE` (`MultiVault.sol:798`); `unpause` is `DEFAULT_ADMIN_ROLE` (`MultiVault.sol:803`).
- **Impact:** While the contract is paused, holders cannot exit their positions — both redemption entry points are gated by `whenNotPaused`. The checklist's SOL-CR-1/CR-2 guidance is that users should be able to withdraw/repay even while a protocol is paused; here a pause is a full freeze, not a deposits-only freeze. No funds are lost (par-backed value remains custodied, redeem is restored on `unpause`), and the pauser is the trusted 4-of-8 Safe (handoff §3), so this is **not attacker-reachable** — it is a centralization/operational property surfaced by the checklist.
- **Exploit path:** None (privileged). A `PAUSER_ROLE` holder pausing during an incident temporarily blocks all exits until `DEFAULT_ADMIN_ROLE` unpauses.
- **Recommendation:** Confirm this is the intended emergency posture. If exit-during-pause is desired (common for solvency-backed vaults), leave `redeem`/`redeemBatch` un-gated (mirroring the deliberate `TrustBonding.withdraw`/`checkpoint` asymmetry documented in handoff §2), or document explicitly that a pause is a global freeze and size the pauser trust accordingly. No source change required if a global freeze is intended.
- **Status:** Open (likely Risk-accepted under the handoff §3 trust model; surfaced for an explicit go-live decision).

| LC-A-02 | `MultiVault.sol:509-534` (esp. `:516`, `:533`) | **Canonical `multicall` sets `_virtualMsgValue = 0` on entry but does not re-zero it on exit (dup Fable-A-02, independently confirmed).** Provably harmless: only `multicallPayable` ever writes a non-zero `_virtualMsgValue`, so inside a canonical `multicall` the slot is `0` for the whole frame, and any payable leg composed inside sees `_effectiveMsgValue() == 0` and reverts through its payment/min-deposit validation. The `hasRolledOverSystemUtilization[epoch]` guard makes the carry run at most once per epoch, and it only *copies* `totalUtilization[lastSystemUtilizationEpoch]` into the current epoch **when the current epoch is still `0`** (`:1138`) — it never adds on top of live activity, and `lastSystemUtilizationEpoch` advances each carry. It affects only the emissions-scaling ratio (hard-capped downstream), never native-value conservation or share minting. No §5.1/§5.6 break. `reinitialize` pre-seeds `lastSystemUtilizationEpoch` (`MultiVault.sol:288`) so the first post-upgrade carry reads a meaningful source. **SOL-Heuristics-13 / SOL-Heuristics-11** — checked and clear on the cluster-A surface. |

### Configuration risk (go-live decision)

### [Informational, config-contingent] Privileged setters lack range validation; `feeDenominator == 0` bricks all fee math (ref: SOL-CR-7, SOL-Basics-Math-6)

- **Location:** `MultiVault.sol:808-855` (`setGeneralConfig` / `setAtomConfig` / `setTripleConfig` / `setWalletConfig` / `setVaultFees` / `setBondingCurveConfig`, all `onlyTimelock`); `MultiVaultCore.sol:268-271` (`_setGeneralConfig` validates only `admin != address(0)`); fee math at `MultiVault.sol:902-904` (`_feeOnRaw` = `amount.mulDivUp(fee, generalConfig.feeDenominator)`).
- **Impact:** The setters assign their config structs with essentially no bounds checking. Most consequential: a `setGeneralConfig` with `feeDenominator == 0` makes every `_feeOnRaw` call revert (division by zero in `mulDivUp`), which bricks all fee-charging create/deposit/redeem paths — a protocol-wide DoS with no non-upgrade recovery. Similarly, `setVaultFees` accepts `entryFee`/`exitFee`/`protocolFee` with no `<= feeDenominator` ceiling, so a mis-set fee could over-charge or underflow `assets - fees` on a redeem. This is the same *shape* as the frontier's Fable-H-01 (unvalidated `emissionsLength`), here on `MultiVault`'s own setters. It is **trusted-admin only** — every setter is `onlyTimelock` (the 3-day parameters `TimelockController` per handoff §3), so it is a governance footgun, not a permissionless exploit.
- **Exploit path:** None permissionless. Requires a malformed value pushed through the parameters timelock.
- **Recommendation:** Add lower/upper-bound validation in the setters (nonzero `feeDenominator`; `entryFee + protocolFee <= feeDenominator`, `exitFee <= feeDenominator`; sane `minShare`/`minDeposit`), mirroring the validator pattern recommended for `CoreEmissionsController`. The 3-day timelock plus off-chain review is the current mitigation; validation makes the footgun unreachable.
- **Status:** Open (config/parameterization gate; low priority given timelock gating).

### Open questions for the developer

- **OQ-1 — On-behalf value/attribution split in `createAtomsFor` / `createTriplesFor` inside `multicallPayable`.** The on-behalf create legs attribute the created shares **and** the utilization to `creator` (`MultiVaultLib.sol:210,231,585,670`) while the native value is drawn from the caller's per-leg `values[i]`. The caller must hold `creator`'s CREATION approval (`MultiVaultLib.sol:206,227`), and `msg.sender` is preserved across the `delegatecall`, so this is the intended sponsor-pays / creator-owns semantic. Confirm that crediting the *creator's* utilization (which feeds TrustBonding emissions) for value paid by a *sponsor* is intended and cannot be leveraged to farm utilization beyond the per-epoch emissions cap. (Bounded: utilization requires real locked value and emissions are hard-capped; noted as an economics question, not a cluster-A conservation break.)
- **OQ-2 — Value-bearing legs and the reentrancy model rely on "no untrusted external call inside a payable leg."** The safety of the per-leg `_virtualMsgValue` window rests on the create/deposit legs making only **view** calls to trusted protocol contracts (registry, factory, TrustBonding) before completing, and on `redeem` (the only value-out path) being excluded from the allowlist. When cluster C lands (`recordDeposit`/`recordRedeem` payable hooks that forward native TRUST to a curve), re-audit this: a payable record hook called mid-leg is exactly the untrusted external call this model currently does not have. Confirm the curve hook dispatch will run **after** the leg's `nonReentrant`-guarded state changes and cannot observe a live `_virtualMsgValue`.

## Acknowledged non-issues (properties checked and cleared)

Each line is a §5.6 / §5.1 (cluster-A) hypothesis that was **attempted and refuted**, with the defending guard and the exercising test cited.

- **PASS — `msg.value` replay across legs (§5.6, SOL-EC-2, SOL-Basics-AL-11).** Tried crediting the same wei to two legs. Defended: `multicallPayable` enforces `total == msg.value` (`MultiVault.sol:599`), sets `_virtualMsgValue = values[i]` per leg (`:605`), and the library reads only the passed `payment` param — `grep` confirms **zero** `msg.value` reads in `MultiVaultLib` logic. Each leg is bounded by `values[i]` (single `deposit` uses `payment`; `depositBatch`/create require `sum(assets) == values[i]` via `_validatePayment`, `MultiVaultLib.sol:1315-1333`). Proven by `MulticallPayableValueAccounting.t.sol::test_multiSubcallSuccess_creditsEachSubcallItsAllocatedValue`, `MulticallPayableAdversarial.t.sol::test_multicallPayable_zeroValueDepositCannotReplayOuterValue` and `..._depositBatchCannotBorrowValueFromSiblingSubcall`.
- **PASS — transient state not cleared on a caught revert (§5.6).** Tried leaking `_virtualMsgValue`/`_inMulticall` into a later same-tx call after a leg reverts. Defended by EIP-1153 frame semantics: `multicallPayable` re-throws the first leg revert (`MultiVault.sol:607-611`), reverting the whole frame and rolling back its transient writes; no `try/catch` swallows it. Proven by `TransientReentry.t.sol::test_failedMulticallPayableDoesNotLeakTransientStateIntoLaterCallInSameTx` and `MulticallPayableValueAccounting.t.sol::test_multiSubcallCaughtRevert_doesNotLeakVirtualValue` (later direct deposit is credited its own value, not the stale one).
- **PASS — re-entry into a payable leg via an external call while `_virtualMsgValue` is set (§5.6).** Tried re-entering `deposit`/`redeem`/`multicall`/`multicallPayable` from a `redeem` receive hook. Defended: (a) create/deposit legs make **no** untrusted external call (only trusted **view** calls to registry/factory/TrustBonding); (b) all six `_effectiveMsgValue()` readers are `nonReentrant` and share one guard slot, so any re-entry during a leg reverts; (c) `redeem` (the only value-out path) is not in the allowlist. Proven by `TransientReentry.t.sol::test_redeemReceiverCannotReenter{Deposit,Redeem,CanonicalMulticall,PayableMulticall}` (all revert with `ReentrancyGuardReentrantCall`).
- **PASS — nested multicall (§5.6).** Tried composing `multicall`/`multicallPayable` inside an active multicall. Defended twice: the payable selector allowlist rejects the multicall selectors up front (`MultiVault.sol:587-592`), and the `_inMulticall` transient guard rejects nesting (`:514,579`). Proven by `Multicall.t.sol::test_multicallPayable_inner{Canonical,Payable}Multicall_rejected_byAllowlist` and `test_multicall_nested{Canonical,Payable}_revertsWith_NestedMulticall`.
- **PASS — off-by-one between `data` and `values`.** `data.length != values.length` reverts `ArraysNotSameLength` (`MultiVault.sol:580`); `sum(values) != msg.value` reverts `MulticallValueMismatch` (`:599`). Proven by fuzz `Multicall.t.sol::testFuzz_multicallPayable_mismatchAlwaysReverts` (10,000 runs) and `test_multicallPayable_revertsOn_LengthMismatch` / `_ValueMismatch`.
- **PASS — selector-allowlist confusion / short calldata (SOL-LL-1/2, SOL-Basics-Function-6).** The allowlist reads `bytes4(data[i][:4])` — the exact bytes the Solidity dispatcher keys on — and rejects `< 4`-byte calldata (`MultiVault.sol:585`). A disallowed selector (e.g. `redeem`) reverts `PayableMulticallSelectorNotAllowed`. Proven by `Multicall.t.sol::test_multicallPayable_revertsOn_{ShortCalldata,DisallowedSelector_redeem}` and the `allows*Selector` positives.
- **PASS — conservation direct-vs-multicall for every allowlisted selector (§5.1).** Each of the six selectors produces byte-identical state whether called directly or as a leg (balance, terms, protocol fees, utilization, vault totals, shares, attribution). Proven by `Multicall.t.sol::test_diff_{createAtoms,createAtomsFor,createTriples,createTriplesFor,deposit,depositBatch}_directVsMulticallPayable` and `MulticallPayableAdversarial.t.sol::test_multicallPayable_allAllowedSelectorsMatchSeparateCallsExactly`.
- **PASS — `msg.sender` preservation across the `delegatecall` legs (SOL-EC-14).** Legs dispatch via `address(this).delegatecall`, preserving the outer caller; approval/attribution checks (`_isApprovedToCreate/Deposit/Redeem`) evaluate the real caller. Proven by `Multicall.t.sol::test_multicallPayable_msgSender_preservation`.
- **PASS — stray-value / locked-ETH (SOL-Basics-Payment-3/7, SOL-Heuristics-14).** `MultiVault` has **no** `receive()`/`fallback()` (grep-confirmed) — all inbound native value flows through the seven payable functions and is payment-validated; canonical `multicall` is non-payable. All custodied value has an exit (`redeem`, `sweepAccumulatedProtocolFees`, `claimAtomWalletDepositFees`). The only permanently-locked value is the intended `minShare` ghost-share seed minted to `BURN_ADDRESS` (`MultiVaultLib.sol:1184`), a deliberate first-depositor / donation-attack mitigation (**SOL-AM-DA-1**), not a leak.
- **PASS — CEI on the value-out paths (SOL-EC-13, SOL-AM-ReentrancyAttack-2).** `_processRedeem` burns shares and writes vault totals (`MultiVaultLib.sol:847-848`) **before** `Address.sendValue` (`:850`); `claimAtomWalletDepositFees` zeroes the accrual (`MultiVault.sol:784`) before sending (`:787`); both are `nonReentrant`. Read-only-reentrancy during the redeem callback observes already-decremented state.
- **PASS — division-by-zero / denominator (SOL-LL-5, SOL-Basics-Math-6) on the hot path.** Under checked 0.8.29 arithmetic, `_validatePayment` uses `+`, and the value loop's `total += values[i]` is checked; there is no attacker-set denominator on the multicall path (the one admin-set denominator is the config-risk item above).
- **PASS — `reinitialize(2)` front-running / re-run (SOL-Basics-Initialization-3, SOL-Basics-PU-2).** `reinitialize` is `onlyRole(DEFAULT_ADMIN_ROLE) reinitializer(2)` (`MultiVault.sol:278`); it reverts once `_initialized >= 2` and is admin-gated, so it is neither front-runnable nor replayable. `initialize` is `initializer`-gated with `_disableInitializers()` in the constructor (`:239-241`).
- **PASS — admin cannot pull user backing (SOL-CR-3, SOL-AM-RP-1).** No admin path withdraws vault backing; `sweepAccumulatedProtocolFees` only forwards separately-tracked `accumulatedProtocolFees[epoch]` to the fixed `protocolMultisig` (`MultiVault.sol:858-867`), and is permissionless (no attacker gain — funds route to the protocol, not the caller).
- **PASS — `tx.origin` / arbitrary low-level call / unbounded loop (SOL-Basics-AC-7, SOL-Basics-Function-6, SOL-Basics-AL-9).** No `tx.origin`; the only low-level calls are `delegatecall` to `address(this)` (trusted, self) and `Address.sendValue`; batch/multicall loops are bounded by `MAX_BATCH_SIZE` and `data.length` with checked iteration.
