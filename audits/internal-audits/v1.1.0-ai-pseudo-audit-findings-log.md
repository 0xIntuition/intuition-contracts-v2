## Findings

### Fable-E-01: ERC-1271 `isValidSignature` verifies the raw digest — no wallet binding (cross-wallet replay)

- Severity / Confidence / Status: **Medium / High / Open**
- Cluster + affected code: E — `src/protocol/wallet/AtomWallet.sol:341-346` →
  `src/libraries/CoinbaseSmartWalletLib.sol:102-161` (EOA verify at `:146`, passkey challenge `abi.encode(hash)` at
  `:157`). Unused wrapper: `replaySafeHash`/`domainSeparator` at `CoinbaseSmartWalletLib.sol:303,311`.
- Invariant broken: authorization boundary — a signature scoped to one account authorizes an action on a different
  account.
- Attacker capability: permissionless relayer/spender that receives one legitimate ERC-1271 signature, where (a) the
  signer's key/passkey owns ≥2 AtomWallets (the normal case — one EOA claims many atom wallets) and (b) the consuming
  integration produces a digest not bound to the wallet account (canonical case: Permit2 `SignatureTransfer`, which
  signs token/amount/spender/nonce/deadline + the Permit2 domain, but not the owner account).
- Attacker sequence (PoC outline):
  1. setup: Alice's key owns `walletA` and `walletB`; both hold token T; both approve Permit2.
  2. Alice signs one Permit2 permit intending `walletA`; the digest `H` does not encode `walletA`.
  3. `walletA.isValidSignature(H, sig) == 0x1626ba7e` (intended).
  4. assertion that fails: the same `sig` yields `walletB.isValidSignature(H, sig) == 0x1626ba7e` — a wallet Alice never
     targeted, so a Permit2 transfer can be replayed on `walletB`.
- Impact: cross-wallet signature/approval replay across a user's co-keyed AtomWallets under owner-unbound EIP-712
  integrations; funds risk under Permit2/AllowanceTransfer. (Seaport binds the offerer and is unaffected.)
- Root cause: upstream Coinbase Smart Wallet wraps the input in `replaySafeHash(hash)` (EIP-712 domain = chainId +
  `address(this)`) before verifying; this port verifies the raw `hash` and never calls the
  `replaySafeHash`/`domainSeparator` it still ships. Nothing in the ERC-1271 path references `address(this)`, so
  acceptance is account-independent. The UserOp path is unaffected (`userOpHash` binds `sender`+chainId+nonce).
- Refutation attempted: checked whether differing `owner()`/registry between two wallets rescues it (no — identical
  owner key ⇒ identical acceptance); whether the UserOp/ERC-1271 prefix asymmetry blocks reuse (blocks UserOp↔ERC-1271,
  not ERC-1271↔ERC-1271 across wallets); Seaport (offerer-bound, safe); Permit2 SignatureTransfer (not owner-bound,
  replayable). Refutation fails.
- Recommendation: verify against `CoinbaseSmartWalletLib.replaySafeHash(hash, name, version)` (already implemented)
  instead of the raw `hash`, or otherwise mix `address(this)`+chainId into the challenge. If raw-digest verification
  must be retained, drop the Permit2 compatibility claim from the NatSpec at `AtomWallet.sol:334`.
- Regression test: two wallets, same owner key, one signature — validates on target, **fails** on the sibling once
  binding is added; assert `isValidSignature` output changes when only `address(this)` differs. Mutation-check: the new
  test must go red if the `replaySafeHash` wrap is removed.
- Variant sweep: EOA owner — same bug; WebAuthn/passkey owner (`abi.encode(hash)` challenge,
  `CoinbaseSmartWalletLib.sol:157`) — same bug; ERC-1271 contract owner via the Solady fallback — same bug. UserOp path
  — safe (bound). Single/batch/on-behalf/preview/router — n/a (this is the ERC-1271 read path).

### Fable-D-01: Idle-window `setClaimCapWindow` retune carries a stale count into a fresh window

- Severity / Confidence / Status: **Low / High / Open**
- Cluster + affected code: D — `src/protocol/wallet/AtomWarden.sol:728-736` (`_setClaimCapWindow`), interacting with
  `:750-768` (`_consumeClaimCapBudget`).
- Invariant broken: n/a — window accounting correctness. The defect is in the **safe** direction (denial, not bypass).
- Attacker capability: none — triggered by ordinary honest admin ops. Preconditions: (a) window W accrued ≥1 counted
  claim; (b) ≥1 full subsequent window elapses with zero `claimWithAuthorization` calls (so no claim reset the stale
  counter); (c) admin calls `setClaimCapWindow` during that idle window.
- Attacker sequence (PoC outline):
  1. cap=2, window=1 day; two claims in window W ⇒ `claimsInWindow=2`, `currentClaimWindowId=W`.
  2. warp `+WINDOW+1` (now in W+1, but state still anchored to W since no claim reset it).
  3. admin `setClaimCapWindow(12h)`: `_setClaimCapWindow` re-anchors `currentClaimWindowId` but preserves
     `claimsInWindow=2`.
  4. assertion that fails: an honest `claimWithAuthorization` now sees `windowId == currentClaimWindowId` ⇒ no reset ⇒
     `claimsInWindow(2) >= cap(2)` ⇒ reverts `AtomWarden_ClaimCapExceeded`, despite a full window having passed. Control
     without the retune succeeds.
- Impact: temporary denial of the signed-quorum claim path after an admin window retune; self-heals at the next
  re-anchored rollover. No fund loss, no cap bypass (strictly over-restrictive).
- Refutation attempted: tried to convert to an under-throttle (fresh-budget mint) via long→short and short→long retunes
  on a live window — count is preserved both directions; the defect only manifests as over-throttle.
- Recommendation: before re-anchoring, settle any pending rollover under the old divisor — fold the
  `windowId != currentClaimWindowId ⇒ reset` logic that `_consumeClaimCapBudget` already uses into `_setClaimCapWindow`.
- Regression test: `test_idleWindowRetune_overThrottles` + control `test_idleWindow_noRetune_claimSucceeds`.
- Variant sweep: single-claim confirmed; independent of batch/threshold; live-window retunes (long→short, short→long)
  preserve count (safe); `setMaxClaimsPerWindow` unaffected (never touches `currentClaimWindowId`).

### Fable-E-02: `transferOwnership` bypasses the primary-owner-removal invariant

- Severity / Confidence / Status: **Low / High / Open**
- Cluster + affected code: E — `src/protocol/wallet/AtomWallet.sol:252-274` (`transferOwnership`, unconditional
  `removeOwnerByAddress(oldOwner)` at `:268`) vs the guard at `:407-412` (`removeOwnerAtIndex` →
  `AtomWallet_OwnerCannotBeRemoved`).
- Invariant broken: the advertised "primary `owner()` cannot be removed" invariant.
- Attacker capability: any registered co-owner (added by the primary), gated by `onlyMultiOwnableOwnerOrSelf`.
- Attacker sequence (PoC outline):
  1. primary claims `walletA` (index 0); primary adds `coSigner` (index 1).
  2. direct `removeOwnerAtIndex(0, abi.encode(primary))` reverts `AtomWallet_OwnerCannotBeRemoved` (guard works).
  3. `coSigner` calls `transferOwnership(coSigner)`; internally `removeOwnerByAddress(primary)` deletes the primary and
     `_claimant` becomes `coSigner`.
  4. assertion: `owner() == coSigner` and `isOwnerAddress(primary) == false`.
- Impact: the "primary owner cannot be removed" guarantee is not a real trust boundary — a co-owner can evict the
  primary. **Low, not High:** in the flat MultiOwnable model a co-owner is already fully privileged, so eviction grants
  no new capability; the risk is a false sense of protection for operators who add convenience co-signers.
- Refutation attempted: looked for a path where a co-owner is genuinely subordinate — none; every owner-gated function
  uses the same `isOwnerAddress` check. Confirmed the eviction installs a new owner atomically (cannot brick the
  wallet).
- Recommendation: either make `transferOwnership` refuse to remove the current primary when `msg.sender != owner()`, or
  drop the misleading `removeOwnerAtIndex` primary-owner guard and document the flat trust model. Consistency over the
  specific choice.
- Regression test: co-owner `transferOwnership(self)` reverts once the fix is adopted; primary rotating itself still
  succeeds.
- Variant sweep: `removeOwnerByAddress` is reachable only from `transferOwnership`; `renounceOwnership` is hard-disabled
  (`AtomWallet.sol:280-282`).

### Fable-H-01: `emissionsLength` accepted without a non-zero validator → protocol-wide DoS on misconfig

- Severity / Confidence / Status: **Low / High / Open**
- Cluster + affected code: H — `src/protocol/emissions/CoreEmissionsController.sol:46-64`
  (`_EPOCH_LENGTH = emissionsLength` at `:61` with no validator; contrast the four other params each validated at
  `:130,136,142,148`).
- Invariant broken: n/a — every schedule parameter should be range-checked at init.
- Attacker capability: none — reachable only via `SatelliteEmissionsController.initialize` (`initializer`-gated, 4-of-8
  Safe). Trusted-admin footgun, filed per the "note trusted-admin actions separately" mandate.
- Attacker sequence (PoC outline):
  1. initialize with `emissionsLength = 0`.
  2. `_calculateTotalEpochsToTimestamp` (`:217`) computes `(timestamp - start) / _EPOCH_LENGTH` = division by zero ⇒
     every `getCurrentEpoch`/`getEpochAtTimestamp`/`getEpochTimestampEnd` reverts.
  3. assertion: because `TrustBonding` routes all epoch math through the satellite
     (`TrustBonding.sol:154,296,345,548,552`), the entire bonding/claim system is bricked with no non-upgrade recovery
     (no post-deploy schedule setter).
- Impact: protocol-wide DoS on a single fat-fingered init value; silent (deploys fine, reverts on first epoch query).
- Refutation attempted: searched for any other guard on `_EPOCH_LENGTH` (none); confirmed no post-deploy setter to
  recover without a proxy upgrade.
- Recommendation: add `if (emissionsLength == 0) revert CoreEmissionsController_InvalidEmissionsLength();` (optionally
  an upper bound) alongside the other validators.
- Regression test: `test_init_revertsWhenEpochLengthZero`.
- Variant sweep: only `emissionsLength` lacks a validator; the other four params are covered and tested.

### Informational

- **Fable-A-01** — Single `deposit` leg (`MultiVaultLib.sol:235-252`) skips `_validatePayment` unlike the
  create/`depositBatch` legs (`:173,188,209,230,267`). No divergence: `payment = _effectiveMsgValue = values[i]` is the
  whole deposit, there is no `assets[]` to diverge from, and `multicallPayable` enforces `sum(values)==msg.value`.
  Optional: comment the deliberate asymmetry. Status Open.
- **Fable-A-02** — Canonical `multicall` (`MultiVault.sol:514-533`) forces `_virtualMsgValue = 0` on entry (`:516`) but
  clears only `_inMulticall` on exit (`:533`). Provably no leak (the slot is 0 for the whole call). Optional: add
  `_virtualMsgValue = 0` at `:533` for symmetry (redundant). Status Open.
- **Fable-B-01** — `MultiVaultLib.sol:93` NatSpec references a "storage-layout diff gate verified by …" that does
  **not** exist in CI (no committed golden snapshot, no `.github` `forge inspect` step). Mirror integrity currently
  rests on runtime `vm.load` tests only, which pin load-bearing slots but not every packed field, so a future retype
  could pass. Recommendation: add a `forge inspect … storage` golden-snapshot CI gate (same gap exists for the
  TrustBonding mirror). Status Open.
- **Fable-D-02** — Fixed-window limiter (`AtomWarden.sol:750-768`) admits exactly `2×cap` claims across a boundary
  straddle (documented at `:743-746`). Inherent to fixed windows; size the cap accordingly. Status Open (by design).
- **Fable-E-03** — ERC-1271 ECDSA path (`CoinbaseSmartWalletLib.sol:146`, Solady `isValidSignatureNow`) accepts high-s
  (malleable) signatures. Not an auth bypass (still needs the key) and irrelevant to the nonce-bound 4337 path; only
  matters to off-chain integrators that dedup by signature bytes, and it compounds Fable-E-01's surface. Status Open.
- **Fable-E-04** — `_validateSignature` (`AtomWallet.sol:500`) returns `_packValidationData(!isValid, 0, 0)` — no
  `validUntil`/`validAfter`. Documented intentional; EntryPoint nonce still prevents replay. Status Open (by design).
- **Fable-F-01** — `claimRewards` is `whenNotPaused` (`TrustBonding.sol:383`) and only ever targets `currentEpoch-1`
  (`:396`), so a pause straddling an epoch boundary permanently forfeits one epoch's reward for users (tokens are
  reclaimed/burned, not stolen; no double-claim). Recommendation: document that pauses should not straddle epoch
  boundaries, or allow claiming the last N epochs. Status Open (by-design tradeoff).
- **Fable-F-02** — `deposit_for` pulls from the lock holder, not `msg.sender` (`VotingEscrow.sol:367-389`), so a third
  party can force-extend a victim's lock up to the victim's outstanding allowance. `whenNotPaused`
  (`TrustBonding.sol:448`); cannot mint or double-claim rewards. Mitigation (already in NatSpec): tight allowances.
  Status Open (inherited semantics).
- **Fable-F-03** — `_getSystemUtilizationRatio` (`TrustBonding.sol:660-661`) reads raw `totalUtilization[epoch]` (not
  self-healing) while `_getPersonalUtilizationRatio` uses the self-healing 3-slot lookback
  (`MultiVaultLib.sol:520-541`); after a multi-epoch quiet gap the system ratio can be pushed to its 100% ceiling.
  Bounded: the ratio only scales emissions to the funded `maxEmissions`, never above, and claims are hard-capped per
  epoch — no solvency/conservation break. Status Open.
- **Fable-G-09** — FeeProxy `receive()` (`FeeProxy.sol:550-554`) accepts ETH only from `multiVault`/self and there is no
  sweep; any stray ETH is **locked**, never stealable, so it can only cause the proxy to under-pay, never over-pay (does
  not break §5.1). Revisit only if MultiVault later refunds callers. Status Open.
