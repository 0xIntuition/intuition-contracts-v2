## Findings

### TOB-01: ERC-1271 raw-digest validation enables cross-account / cross-chain signature replay
- Severity / Confidence / Status: **Medium / Medium / Open**
- Provenance: checklist round, Cluster E
- Cluster + affected code: `src/protocol/wallet/AtomWallet.sol:341-346` (`isValidSignature`); dead helpers `src/libraries/CoinbaseSmartWalletLib.sol:303-321,398` (`replaySafeHash` / `domainSeparator`, zero call sites)
- Checklist anchor: SOL-Signature-1 (replay / `block.chainid` in the signing scheme), SOL-AM-ReplayAttack-2 (cross-chain signature replay), SOL-Heuristics-9 (protocol contracts as actors)
- Invariant broken: trust boundary (§6.E — "`isValidSignature` must reject non-owners" widened to "must not authorize a signature intended for a different account")
- Attacker capability: permissionless, given the realistic precondition that one key (EOA or P-256 passkey) owns more than one `AtomWallet` — the expected case when a single person claims several atoms — or the same wallet address exists on a second chain.
- Attacker sequence (PoC outline):
    1. setup: key `K` is a MultiOwnable owner on `AtomWallet_A` (atom A) and `AtomWallet_B` (atom B).
    2. A dApp obtains an ERC-1271 signature from `K` over digest `H` intended for wallet A (`AtomWallet_A.isValidSignature(H, sig) == 0x1626ba7e`).
    3. relayer replays the identical `(H, sig)` to `AtomWallet_B.isValidSignature(H, sig)` → also returns `0x1626ba7e`, authorizing an action attributed to B. Same digest replays across chains for an equal wallet address (no `chainId` binding).
    - assertion that fails: `isValidSignature` returns the magic value for a wallet the signature was not scoped to.
- Impact: bounded to integrations whose signed digest does not itself embed the exact validating account. Permit2 / Seaport embed `owner`/`offerer` and are safe; generic message-signing, login/session, and some order-book flows keyed on the ERC-1271 signer identity are exposed. No direct theft of vault principal; scope is unauthorized action attribution / session forgery on integrating dApps.
- Refutation attempted: checked whether the 4337 path shares the flaw — it does not: `_validateSignature` (`AtomWallet.sol:498-499`) prefixes `userOpHash`, which the EntryPoint already binds to `sender` + `chainId`, so UserOps are account-scoped. The gap is ERC-1271-only. Confirmed by grep that `replaySafeHash`/`domainSeparator` (which would restore `verifyingContract`+`chainId` binding) are defined but never called.
- Note on intent: the NatSpec at `AtomWallet.sol:333-334` states the raw-digest behavior is deliberate ("Compatible with EIP-712 integrations … that pass the final typed-data digest"). The finding is that this pushes the account-binding obligation entirely onto every integrator; a wallet-side `replaySafeHash` wrap would make it robust by default. Confirm whether the design intends to accept this integrator burden.
- Recommendation: wrap the digest in the already-present `CoinbaseSmartWalletLib.replaySafeHash(hash, "AtomWallet", version)` before validation (matching upstream Coinbase `ERC1271`), or document a hard integration requirement that all ERC-1271 digests must bind this account address and `chainId`.
- Regression test: `test_isValidSignature_rejectsCrossWalletReplay`, `test_isValidSignature_bindsChainId` (both net-new — no `AtomWallet`/factory tests exist in the tree).
- Variant sweep: single = same bug (any direct `isValidSignature` call); batch / on-behalf / preview / router / upgrade = n/a (ERC-1271 is not reached through those paths); 4337 UserOp path = safe (account-bound via EntryPoint).

### TOB-02: `claimRewards` pause across a full epoch permanently forfeits prior-epoch rewards
- Severity / Confidence / Status: **Medium / High / Open**
- Provenance: checklist round, Cluster F
- Cluster + affected code: `src/protocol/emissions/TrustBonding.sol:383` (`claimRewards` is `whenNotPaused`), `:396` (`prevEpoch = currentEpoch() - 1` is the only claimable epoch), NatSpec `:28-29` and `src/interfaces/ITrustBonding.sol:270-274` (rewards for epoch `n` are claimable only during `n+1`, else forfeited); unclaimed remainder path `:355-376`.
- Checklist anchor: SOL-CR-2 (pause mechanism — user accounting under pause), SOL-AM-GA-1 (griefing that blocks a user withdrawal/claim), SOL-Heuristics-16 (asymmetry: locks pause, but the escape/claim half interacts badly with the single-epoch window)
- Invariant broken: §5 spirit — pausing "cannot be used to grief claims across an epoch boundary" (handoff §6.F). The pause asymmetry is safe for **principal** (`withdraw`/`checkpoint` stay open) but not for **reward claims**.
- Attacker capability: `PAUSER_ROLE` (a trusted role), or any sustained good-faith emergency pause. No attacker profit; the harm is collateral, permanent user-reward loss.
- Attacker sequence (PoC outline):
    1. setup: epoch `n` — users A, B hold veTRUST; the epoch-end snapshot fixes their eligibility.
    2. start of epoch `n+1`: `pause()` is called (incident response or malicious pauser).
    3. pause persists past `epochTimestampEnd(n+1)` (production epoch ≈ 14 days).
    4. epoch `n+2`: `unpause()`. `claimRewards` now computes `prevEpoch = n+1`; epoch `n` is unreachable — no catch-up hook exists.
    - assertion that fails: A/B permanently lose epoch `n` rewards; the forfeited amount is subsequently treated as "unclaimed" and bridged back / burned via `getUnclaimedRewardsForEpoch`.
- Impact: irreversible loss of a full epoch's rewards for **every** eligible user, triggered by any pause that spans a claim window. Bounded loss (one epoch's emissions), no theft.
- Refutation attempted: looked for any alternate or retroactive claim path (admin catch-up, multi-epoch claim, grace window) — none exists; `prevEpoch` is hard-wired and the per-epoch claimed flag prevents re-opening. Confirmed `withdraw`/`checkpoint` remain callable while paused, so principal is never trapped — the loss is strictly the reward claim.
- Recommendation: either make `claimRewards` callable while paused (it is `nonReentrant` and reads settled historical state), or add a post-unpause grace window that re-opens the epoch(s) whose claim window elapsed entirely under pause.
- Regression test: `test_claimRewards_pausedAcrossEpochBoundary_forfeitsPreviousEpochRewards`.
- Variant sweep: single/batch = n/a (one claim entry point); the same class applies to any `whenNotPaused` action whose eligibility window is a single epoch — none other in this contract.

### TOB-03: Global per-window claim cap can starve honest claimants at `signatureThreshold == 1`
- Severity / Confidence / Status: **Minor / High / Open**
- Provenance: checklist round, Cluster D
- Cluster + affected code: `src/protocol/wallet/AtomWarden.sol:750-768` (`_consumeClaimCapBudget`), `:118` (`claimsInWindow` — a single global counter), consumed only after quorum success (`:309`→`:311`)
- Checklist anchor: SOL-AM-GA-1 (external state changeable by others blocks normal user action), SOL-AM-SybilAttack-1 (quorum/utilization mechanism keyed on a shared counter)
- Invariant broken: n/a — griefing / availability
- Attacker capability: a single compromised or malicious `SIGNER_ROLE` key when `signatureThreshold == 1`.
- Attacker sequence (PoC outline):
    1. setup: `signatureThreshold == 1`, `maxClaimsPerWindow == C`.
    2. the compromised signer submits `C` valid `claimWithAuthorization` calls in one window (each against an attacker-controlled `claimant` with a fresh `nonce == 0`).
    3. `claimsInWindow` reaches `C`; every subsequent legitimate signed claim in the window reverts `AtomWarden_ClaimCapExceeded`.
    - assertion that fails: honest claimants cannot claim for the remainder of each window even though their authorizations are valid.
- Impact: temporary, per-window denial of the `claimWithAuthorization` path (other claim paths — `claimOwnershipOverAddressAtom`, `claimAsCreatorAfterExpiry`, operator grants — are unaffected). No fund loss. The cap is consumed only **after** `_verifyQuorum` succeeds, so an attacker cannot burn budget without a valid quorum.
- Refutation attempted: tried to burn cap budget with invalid quorums (rejected — order at `:309`→`:311` means invalid attempts never reach `_consumeClaimCapBudget`); tried to bypass the counter via a different arg (no other input controls it). The griefing survives only at `threshold == 1`; `threshold ≥ 2` defeats single-key compromise outright.
- Recommendation: consider a per-claimant (or per-signer) sub-cap in addition to the global one, or document the global cap's honest-path starvation as an accepted tradeoff and set production `signatureThreshold ≥ 2`.
- Regression test: `test_claimCap_globalStarvationAtThresholdOne`.
- Variant sweep: window retune = safe (see negatives — count preserved); cap-disabled (`0`) = safe (early return).

### TOB-04: `MINTIME ≥ reward epoch length` is a deploy assumption unenforced on-chain
- Severity / Confidence / Status: **Minor / Medium / Open**
- Provenance: checklist round, Cluster F
- Cluster + affected code: `src/protocol/emissions/TrustBonding.sol:202-235` (epoch-end snapshot justified by "MINTIME ≥ EPOCH_LENGTH"), `:137` (`_epochLength` passed to `__VotingEscrow_init`), `src/external/curve/VotingEscrow.sol:110` (only enforces `min_time ≥ 2*WEEK`), `src/protocol/emissions/CoreEmissionsController.sol:61` (`_EPOCH_LENGTH`, immutable, no setter, no cross-check)
- Checklist anchor: SOL-Basics-Function-1 (input validation), SOL-CR-7 (validation in privileged/init setters), SOL-Basics-Initialization-1 (critical state initialized correctly)
- Invariant broken: n/a — config-dependent snapshot safety
- Attacker capability: none directly; the risk materializes only if the deployer sets TrustBonding's `_epochLength` (= `MINTIME`) below the `CoreEmissionsController` epoch length.
- Attacker sequence (PoC outline): under that misconfiguration, a user creates a lock just before an epoch boundary for only `MINTIME`, is counted at near-undecayed weight in that epoch-end snapshot, then lets the lock expire and `withdraw`s it before the reward becomes claimable — yet stays fully eligible because eligibility reads the frozen past snapshot, not the live lock. Result: boundary weight-sniping redistributes rewards toward snipers (no over-emission — the per-epoch budget cap still holds).
- Impact: reward redistribution toward snipers if the two epoch-length parameters diverge. No over-emission, no principal loss.
- Refutation attempted: confirmed the two parameters live in different contracts with no on-chain equality check; confirmed the budget cap (TOB negatives) prevents over-emission regardless.
- Recommendation: add an `initialize` guard tying `_epochLength` (MINTIME) to the `CoreEmissionsController` epoch length (`==` or `≥`), or add a deploy-time assertion and document it as a hard deployment invariant.
- Regression test: `test_initialize_revertsWhenMinTimeBelowSecEpochLength`, `testFuzz_snapshotSnipe_boundedByMintime`.
- Variant sweep: n/a (init-time parameter).

### TOB-06: `feeRecipient` settable to the proxy / MultiVault silently strands affiliate fees

### TOB-07: FeeProxy batch leg proportional-rounding-to-zero reverts the whole batch
- Severity / Confidence / Status: **Minor / High / Open**
- Provenance: checklist round, Cluster G

- Attacker capability: none against third parties (the caller chooses `assets`); self-DoS only.

### TOB-15: Current-epoch reward views read future-dated / in-progress data
- Severity / Confidence / Status: **Informational / Medium / Open**
- Provenance: checklist round, Cluster F
- Affected code: `src/protocol/emissions/TrustBonding.sol:214,230,581` (`userBondedBalanceAtEpochEnd` / `totalBondedBalanceAtEpochEnd` / `_userEligibleRewardsForEpoch` accept `epoch == currentEpoch()`)
- Checklist anchor: SOL-AM-ReentrancyAttack-1 (view returning a not-yet-final value), SOL-Heuristics-13 (state consistency)
- Invariant broken: n/a — not exploitable
- Detail: these snapshot `_balanceOf`/`_totalSupply` at a **future** `_epochTimestampEnd(currentEpoch)` (forward-decayed, i.e. smaller, not inflated) and read still-in-progress MultiVault utilization. They feed only view helpers (`getUserInfo`, `getUserApy`, `userEligibleRewardsForEpoch`); `claimRewards` never uses the current epoch. Integrators reading these get a value that drifts intra-epoch.
- Recommendation: document that current-epoch reward views are provisional, or clamp them to `currentEpoch − 1`.
- Variant sweep: n/a.

### Curve pricing (§5.4 flat-price par; §5.1/§5.2 conservation & solvency)
- PASS — flat-price par cannot extract net-positive — `LinearCurve` is pro-rata: `shares = assets·S/A` and `assets = shares·A/S`, both via `fullMulDiv` rounding **down** (`src/protocol/curves/LinearCurve.sol:180-205`). Deposit-then-redeem round-trips lose at most the fees; no path prices below par or lets a user redeem more than deposited. Exit fees are added to `totalAssets` without minting shares, raising per-share redemption value for remaining holders — a real, redeemable redistribution (not stuck), because pricing is by the `A/S` ratio, not a fixed 1.
- PASS — first-depositor / donation inflation blocked — new non-default vaults seed `minShare` ghost shares to `BURN_ADDRESS` = `0x000000000000000000000000000000000000dEaD` (`MultiVaultLib.sol:1184,1251`); internal accounting tracks `totalAssets` (donations to the contract don't move any vault's `totalAssets`, defeating SOL-AM-DA-1); and a deposit yielding 0 shares reverts (`_validateMinShares`, `MultiVaultLib.sol:1347`). Default-curve vaults can only be initialized via the create paths (`_processDeposit` `:773`).
- PASS — conservation on create/deposit/redeem — traced native flow per operation: create splits `assets` into `atomCreationProtocolFee`+`protocolFee` (→ `accumulatedProtocolFees`), `atomWalletDepositFee` (→ `accumulatedAtomWalletDepositFees`), `minShare` (→ ghost-share backing), and `assetsAfterFees` (→ user-share backing) — the four sum to `assets`. Redeem: `totalAssets −= rawAssetsBeforeFees` but `+= exitFee`; native out = `rawAssetsBeforeFees − protocolFee − exitFee`; `protocolFee` moves to the protocol accumulator; conserved. No underflow: `rawAssetsBeforeFees = shares·A/S ≤ A` since `shares ≤ totalShares`. Checked arithmetic (0.8.29) backstops. `atomDepositFraction/3` dust (≤2 wei) stays as an unattributed positive contract balance — safe, accepted (handoff §7).
- PASS — ghost shares unredeemable — `_validateRedeem` enforces `totalShares − shares ≥ minShare` (`MultiVaultLib.sol:1388-1391`), so the `BURN_ADDRESS` seed is never withdrawn and always backs a defined price.
